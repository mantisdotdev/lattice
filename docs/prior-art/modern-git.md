# Git's modern machinery

> Between roughly 2018 and 2026 Git absorbed a sustained scaling program driven by three institutions with monorepo pain: Microsoft (VFS for Git, then Scalar, then the sparse index — Derrick Stolee, Jeff Hostetler, Victoria Dye), GitHub (commit-graph, multi-pack-index, geometric repacking, production merge-ort — Stolee, Taylor Blau), and GitLab (the core-Git reftable backend — Patrick Steinhardt, implementing Shawn Pearce's 2017 JGit design), with Elijah Newren rewriting merge from scratch as `merge-ort`. Most of the things people say Git cannot do, Git now does — behind configuration. The current line is Git 2.55 (29 June 2026). Git 3.0 will change two storage defaults, but its own `BreakingChanges` document says "There is no planned release date for this breaking version yet"; the widely-repeated "late 2026" target is contributor intent reported secondhand, not a committed date. Everything below is measured against that Git, not against Git 1.7. Claims marked *(local)* were verified against a git 2.50.1 installation; version-sensitive claims are pinned because, as §2 shows, several of them expire.

## 1. What did it get right?

### 1.1 Absence encoded as negative space, not as a manifest
Partial clone marks filtered packfiles with a `.promisor` sidecar next to `.pack`/`.idx`. There is deliberately **no list of missing objects**: an object reachable from a promisor object is *assumed* fetchable. The design doc's arithmetic is explicit — "if there are 100M missing blobs, this file would be at least 2GiB on disk" — and it would need rereading and rewriting on every dynamic fetch. Object-lookup failure instead calls `promisor_remote_get_direct()`; `extensions.partialClone` names the fallback remote. The lesson worth stealing is the inversion: absence is inferred from the provenance of the container, not enumerated per object.

### 1.2 The index made sublinear in repository size
Cone-mode sparse-checkout matches on directories, which lets the index store a **sparse directory entry** — one row carrying "the object ID of the tree at `HEAD`" and marked `SKIP_WORKTREE` — in place of every file beneath it. Index cost falls from O(HEAD) to O(populated). Stolee's monorepo measurements (over 2M files at HEAD, a cone of roughly 100K): index 180 MB → under 10 MB; `git status` 1.3 s → under 200 ms. The migration discipline matters as much as the format: `command_requires_full_index` is "on by default and disabled one builtin at a time," so any unconverted command transparently calls `ensure_full_index()` and is correct-but-slow rather than wrong.

### 1.3 A derived, regenerable reachability index — partly default-on
The commit-graph file stores parent lists plus generation numbers. Generation number v2 is the **corrected committer date**, defined recursively over **parents**: a root commit takes its own committer date; every other commit takes max(its own committer date, largest corrected date among its *parents* + 1). That restores the monotonicity that raw committer dates violate under clock skew. `commitGraph.generationVersion` defaults to 2 and `gc.writeCommitGraph` defaults to true *(local)*, so the topology index is genuinely not an expert feature. Changed-path Bloom filters (Git 2.27) answer "this commit definitely did not touch this path," accelerating `git log -- <path>` and blame — but they are **not** written by default: they require an explicit `git commit-graph write --changed-paths`, after which "future commit-graph writes will automatically assume that this option was intended" *(local)*. Lattice's declared stance — the semantic layer is derived, regenerable, never authoritative — is exactly this pattern, proven at Git's scale.

### 1.4 The filesystem reports; Git stops polling
The built-in FSMonitor daemon registers for OS change notifications and keeps a time-sorted queue of changed paths. Clients exchange **opaque tokens** (a sequence identifier, the daemon PID, and a synchronization ID); a command sends the token stored in its index and receives "everything changed since." If the OS drops events or the daemon falls behind, it declares bankruptcy, issues a new SID, and returns a trivial "assume everything changed" response — a designed-in failure mode rather than silent staleness. GitHub's published numbers, for FSMonitor **plus** the untracked cache together: Chromium (393K files) `git status` 17.6 s → 0.827 s; a synthetic 2M-file tree 85.1 s → 0.750 s. The article does not decompose the two contributions, so any claim about which mechanism supplies which share is unsourced. **This was macOS/Windows-only until Git 2.55, whose release notes state flatly: "The fsmonitor daemon has been implemented for Linux."** The Linux implementation uses `inotify` — chosen over `fanotify` because it needs no elevated privileges — which "requires one watch per directory, so very large repositories may need to raise the `fs.inotify.max_user_watches` limit." Network-mounted repositories remain opt-in.

### 1.5 Merge as a pure function of three trees
`merge-ort` is a from-scratch rewrite whose defining property is that it does not use the index or working tree as scratch space. That one decision unlocked `git merge-tree --write-tree` (2.38) — a merged tree OID plus structured conflict information, computed in a bare repo — and `git replay` (2.44), which rebases without a worktree. It has been the **default merge strategy since Git 2.34**. GitHub reports `ort` outperforming `recursive` "by 500x" on a rename-heavy merge and "over 9000x" across a series of similar merges, the extra factor coming from caching results between merges in a rebase. Their production rollout replaced a libgit2 implementation: merge p50 71.07 ms → 7.74 ms, p99 1.63 s → 329.82 ms, and "730k" rebases costing 2.56 hours under libgit2 versus "under 10 minutes" under merge-ort. They also found their libgit2 path chose merge bases differently from Git itself, so "sometimes a user's local Git could easily merge what our implementation could not."

### 1.6 Maintenance made incremental
The multi-pack-index maps each OID to (pack number, offset) in one sorted table, giving "O(log N) lookup time for any number of packfiles." **Incremental MIDX chains** let a new layer be appended without invalidating earlier layers, addressed by concatenated lexicographic ordering, with a pseudo-pack order formed by concatenating each layer's order; the MIDX document still lists full reachability-bitmap support for chains under future work. `git maintenance` under the `incremental` strategy runs commit-graph and prefetch hourly (prefetch writes to `refs/prefetch/`, leaving remote-tracking refs untouched), loose-objects and incremental-repack daily, pack-refs weekly *(local)*. The geometric-repacking machinery has been in Git since 2.33 and has powered GitHub's own maintenance for years; Git 2.52 exposed it as a `geometric` maintenance task, and Git 2.55 implemented "compaction of MIDX layers" plus an "incremental strategy that does not require all-into-one repacking."

### 1.7 Ref storage rewritten as a log-structured merge stack
Reftable stores refs in prefix-compressed blocks with restart points for binary search, and log records keyed `ref_name '\0' reverse_int64(update_index)` where `reverse_int64(t) = 0xffffffffffffffff - t`, so lexicographic order yields most-recent-first. A repository holds an ordered *stack* of immutable files named `${min_update_index}-${max_update_index}-${random}.ref`, listed oldest-first in `tables.list` and read in reverse; a transaction takes `tables.list.lock`, writes one new file at `max_update_index + 1`, and renames the list into place. All log records in a transaction share an `update_index`, so what changed together stays correlated. The design document's Android measurements (866k refs): packed-refs 62.2 M → 36.1 M; cold by-name lookup 409,660.1 µs → 33.9 µs; reflog storage 173 M → 5 M across 149,932 entries.

### 1.8 Two protocol-v2 capabilities worth copying
Bundle URIs advertise a git-config-format *bundle list* whose `creationToken` is "a nonnegative 64-bit integer used for sorting": clone downloads in decreasing token order until prerequisites are met and unbundles in increasing order; fetch skips tokens not larger than the one it stored; bundled refs land in `refs/bundles/*` and are replayed as `have`s to shrink the subsequent negotiation. The contract worth stealing is explicit — "The remote Git server is the ultimate source of truth, not the bundle URI," and on anything unexpected "Git can ignore that data and continue as if it was not given a bundle URI." Large object promisors reuse the mechanism to advertise a dedicated promisor remote with name, URL, filter-spec (`blob:limit=<size>`) and token, with `git repack --filter=` proposed for separating offloadable blobs. Unlike Git LFS, no up-front decision and no history rewrite — though LOP is a design document positioning itself as "an alternative to Git LFS," not a finished client story.

## 2. Why didn't it win — reframed

Git won and is still winning; the interesting question is where the mitigations fall short and at what cost. (A commonly cited "~94% of developers use Git" figure from Stack Overflow's 2022 survey could not be confirmed against the primary results and is omitted rather than repeated.)

**The fast Git is a different product you have to know exists.** Of the mechanisms in §1, only the commit-graph's topology index and merge-ort are on by default. Partial clone, sparse-checkout, the sparse index (off even *inside* sparse-checkout — "the default is to not use it" *(local)*), changed-path Bloom filters, FSMonitor, MIDX, `git maintenance start` and reftable are each opt-in. Scalar exists *because* the correct configuration is a bundle someone else should assemble: it enables partial clone, cone-mode sparse-checkout, background maintenance and the filesystem monitor, and its own man page describes it as "configuring advanced Git settings" for you. That is an admission from Git's own contributors that discoverability, not capability, is the binding constraint. The VFS-for-Git predecessor died for an unrelated reason worth noting given Lattice's non-goals: "Apple deprecated the kernel features that provided the filesystem virtualization that was required."

**The features compose badly, and the failures are silent performance cliffs rather than errors — but the specific cliffs decay fast.** (i) An unconverted command against a sparse index calls `ensure_full_index()`, and the design doc is blunt: "This will be slower in all cases," because "parsing trees is slower than parsing the index format." Opting in can cost you. (ii) `git sparse-checkout`'s man page still carries "THIS COMMAND IS EXPERIMENTAL" and warns the sparse index "is not completely understood by external tools" *(local)*. (iii) In a blobless clone, `git blame` and `git log -p` fault blobs in one at a time; the partial-clone doc concedes "Dynamic object fetching tends to be slow as objects are fetched one at a time." The mitigation, `git backfill` (2.49), batches by path via the path-walk API — and is itself marked "THIS COMMAND IS EXPERIMENTAL" *(local)*. (iv) **A fourth instance has just expired, which is the point.** As of git 2.50.1, `pack-objects --path-walk` was documented "Incompatible with `--delta-islands`, `--shallow`, or `--filter`" *(local)*, so partial-clone servers could not use the better packing. Git 2.55's release notes record that "`git pack-objects --path-walk` traversal has been integrated with several object filters, including blobless and sparse filters," and the current manual now lists supported forms `blob:none`, `blob:limit=<n>`, `tree:0`, `object:type=<type>`, `sparse:<oid>`. Only `--delta-islands` remains incompatible, and `--use-bitmap-index` is ignored. Any document asserting a Git limitation without a version pin has a shelf life of roughly one release.

**The scaling program is about transfer and traversal, not content representation.** The object model is unchanged: whole-file blobs, zlib-deflated, delta-compressed against neighbours chosen by a name-hash heuristic. Git 2.49's name-hash v2 improved *which* objects get delta'd (microsoft/fluentui: repack "~96 seconds to ~34 seconds", pack "439 MiB to just 160 MiB") — a 2.7x pack-size win from a heuristic change, not a granularity change. The large-object-promisors document draws the boundary in its Non-Goals: "we are not going to discuss pluggable ODBs or other object database backends that could chunk large blobs, dedup the chunks and store them efficiently," and concedes that Git "tries to use delta compression or zlib compression which is unlikely to work well on already compressed binary content." A one-byte edit to a 50 MB incompressible file still writes a new 50 MB object, and no configuration changes that. Note the exact modality, though: the doc calls chunking "a nice improvement" deferred as "a separate effort," not an architectural impossibility.

**Both remaining format transitions are gated by ecosystem, not by correctness — the decisive finding.** The SHA-256 transition has had a complete published design since 2017: a bidirectional translation table, `extensions.compatObjectFormat`, pack idx v3 carrying both hash tables, a `loose-object-idx`. Yet GitHub's summary of Git 2.52 calls the interop work "the first step," and `BreakingChanges` states the requirement as "the ecosystem is ready to support the 'sha256' object format. This includes popular Git libraries, applications and forges," adding "There is no plan to deprecate the 'sha1' object format at this point in time." GitHub still does not host SHA-256 repositories in 2026; GitLab's support exists but is surfaced under "Experimental settings" and advised for test projects only. Reftable's stated prerequisite is likewise that "alternative implementations of Git like JGit, libgit2 and Gitoxide need to support it." Nine years of correct design, blocked on forges.

**What Git still has no mechanism for at all — and one gap that just narrowed.** There is no repository-level operation object: the reflog is per-ref, does not cover index or worktree state, and expires (unreachable entries default to 30 days *(local)*), so undo has nothing to move a pointer to. There is no first-class conflict object: a conflicted merge lives in the index's higher stages and the worktree — uncommitted state that cannot be checkpointed, shared or synced. Provenance is closest to existing: `git notes` stores a tree keyed by object name on `refs/notes/*`, and each edit is a new commit on that ref, so a commit *can* be annotated after the fact without rewriting it. But notes have no schema, are not fetched or pushed by default, merge only via an explicit `git notes merge` with manual resolution in `.git/NOTES_MERGE_WORKTREE` *(local)*, and nothing indexes them. **The narrowing gap is history editing.** Git 2.54 introduced an experimental `git history` command with `reword` and `split`; Git 2.55 added `fixup`. It is a genuinely better front-end than interactive rebase — but it is still a rewrite: it produces new commit IDs and "by default updates all branches that are descendants of the original commit to point to the rewritten commit" (`--update-refs=head` narrows it). Git is investing in making rewriting *pleasant*, not in making projection possible. Lattice's pillar-2 claim survives on substance; its UX margin is shrinking.

## 3. What will Lattice do differently, concretely?

**G1.8 (chunking: p95 < 262,144 new bytes for a 1-byte edit in a 50 MB file) — genuinely differentiating, with a caveat about modality.** No Git configuration matches this, and Git's own design document puts chunking-and-dedup outside its scope. Keep it as the headline storage claim, but state the boundary honestly: it is a scope decision Git has deferred to "a separate effort," not something Git's object model forbids. **Commitment: the G1.8 rationale in the storage ADR must quote the large-object-promisors Non-Goals verbatim and state that the claim is "no shipped Git configuration," not "impossible for Git."**

**G1.9 (store ≤1.25x restic, ≤1.5x `git gc --aggressive`) — correctly calibrated; the baseline needs a version pin.** Name-hash v2 changed pack size by 2.7x on at least one real repo. **Commitment: `bench/ENVIRONMENT.md` pins the exact git version and build for the G1.9 baseline; the baseline is produced by Git ≥ 2.55 with `git repack -adf --path-walk --name-hash-version=2`, with the `--path-walk` filter-compatibility note recorded. A pre-2.49 baseline silently flatters Lattice.**

**G1.5 (`ltx status` p95 < 100 ms, watcher resident) — matching, and unevaluable as stated.** Git's resident-watcher answer measured 0.827 s on 393K files and 0.750 s on a 2M-file tree, and since Git 2.55 it runs on Linux too, so "Lattice has a watcher and Git does not" is false in 2026. **Commitment: the G1.5 harness emits the reference repo's tracked-file count and directory count, plus a same-machine, same-tree `git status` p95 with `core.fsmonitor=true` AND `core.untrackedCache=true` (both, since the published Git numbers are for the pair and are not decomposable), reported alongside the Lattice number — the dual-baseline discipline G1.9 already uses.** **Second commitment: add gate G1.5b — on Linux, the LTX watcher subsystem must degrade to a bounded-cost rescan, not fail, when `fs.inotify.max_user_watches` is exhausted, and the harness must record watches consumed against the limit for the reference repo.** Git's Linux daemon takes one inotify watch per directory; Lattice inherits the identical kernel ceiling and has not yet priced it.

**G1.7 (`ltx log` p95 < 100 ms) — matching for topology, narrower than assumed for paths.** Corrected committer dates are default-on (`commitGraph.generationVersion=2`), but changed-path Bloom filters are not — they need an explicit `--changed-paths` write. So Lattice's edge is default-on-ness, a product decision, not a capability. **Commitment: drop latency from the `ltx log` differentiation claim and let G2.7 (lens integrity, 0 information-loss failures over ≥10,000 generated cases) carry it. Where G1.7 latency is still reported, `bench/ENVIRONMENT.md` must state whether the Git baseline repo had changed-path Bloom filters written, because that single flag moves path-scoped `git log` by an order of magnitude.**

**G5.8 (initial transfer ≤25% of full store) — matching at best.** `--filter=blob:none` routinely beats 25% on blob-heavy repos. `--filter=tree:0` beats it further, but GitHub "strongly recommend[s] that developers do not use treeless clones for their daily work," because `git log -- <path>` in one "will start downloading root trees for almost every commit in the history" — so it is not a legitimate baseline for a developer workflow. Git's real weakness is the *cliff after* the clone. **Commitment: pair G5.8 with a second measured value — request count and p95 latency of the first path-scoped history-with-contents query (`ltx log -p <path>` and the blame equivalent) in a partially-materialized workspace, against the same operations in a `--filter=blob:none` Git clone both with and without `git backfill` having been run. That is the half of the trade Git loses, and `git backfill` is the strongest form of Git's answer.**

**G1.1 (crash safety, 0 failures over ≥2000 SIGKILL + ≥1000 torn-write injections) — differentiating as a gate, not as a capability.** Git has had `core.fsync` and `core.fsyncMethod` since 2.36, with the `batch` method added in **2.37** (not 2.36). The documented default is equivalent to `core.fsync=committed,-loose-object`, which the docs themselves say "risks losing recent work in the event of an unclean system shutdown" *(local)*. **Commitment: the G1.1 claim reads "durability is a measured invariant rather than a configuration knob," and no Lattice document asserts that Git lacks a durability story.**

**G1.3 (universal undo, 0 failures over ≥100k sequences) — genuinely differentiating, and reftable is the blueprint.** **Commitment: ADR-OPLOG specifies the operation log as reftable's structure applied to operations — a monotonically increasing 64-bit `update_index` per operation, an ordered stack of immutable append-only segments named by their index range with a `tables.list` equivalent read newest-first under a `.lock` rename protocol, and geometric compaction — so that `ltx undo` is a stack-head move to `update_index N-1` plus a pre-image root-hash pointer, not an inverse-patch application. The ADR must also adopt reftable's transaction-correlation property: all records written by one operation share an `update_index`, which is what makes "undo the merge, including its ref moves" a single-index operation.** Reftable's 33.9 µs cold by-name lookup over 866k records is the existence proof that this shape is fast enough.

**G5.1/G5.2/G5.4 (provenance) — differentiating, but for a narrower reason than the spec claims.** Git *can* attach post-hoc attestations without rewriting, via notes; what it lacks is schema, default transport, automatic merge, and an index. **Commitment: G5.4's ≤200 ms p95 for `ltx trace --agent --unreviewed --touching src/auth/` is reported against an explicit Git-side baseline — `git log --notes=<ref> --format=… -- <path>` with external filtering, on a commit-graph built with `--changed-paths` — so the number reads as a claim about *indexing*, which is where the difference actually is.**

**G3.1/G3.3 (Git bridge fidelity; 0 teammate-visible anomalies) — the gate most at risk from a moving target.** **Commitment: the G3.3 teammate suite and the G3.1 round-trip corpus each include at least one `--object-format=sha256` repository and one `--ref-format=reftable` repository, plus one repository carrying commits produced by `git history fixup`/`reword`/`split` (so bridge fidelity is tested against Git's new rewrite front-end, not only `rebase`); `bench/ENVIRONMENT.md` records the Git version. A suite pinned to Git 2.50.1 measures a Git that will be legacy on the day Lattice ships.** Note the timing correction: Git 3.0 is undated in its own `BreakingChanges` doc, so the risk is not a deadline but an unpredictable arrival.

### Residual risk for Lattice

1. **Unbundling is why Git's mitigations shipped at all.** Lattice reads partial clone and sparse index as "bolt-ons." The other reading is that they are *separable*, and therefore adoptable one at a time inside an unchanged ecosystem. Lattice's equivalents are welded into the format: a team cannot take Lattice's chunking without taking Lattice. G3 is the only bridge, and G3.3's target of zero anomalies is carrying load no other gate can share.
2. **Degraded mode has a measured cost in Git, and Lattice has not priced it.** `ensure_full_index()` is Git's version of "the derived layer degrades silently," and the design doc says it "will be slower in all cases." G4.5 checks that Lattice's degradation is flagged and non-fatal; G4.6 measures the semantic/raw ratio only in semantic mode. Nothing measures that degraded structural mode is not slower than `--raw`. That gate does not exist yet.
3. **G5.8 and G2.3 are in tension.** Partial clone introduces a workspace that does not hold all content. Every system that has done this needed a user-visible concept for it (promisor remote, filter spec, `git backfill`). Lattice's seven nouns contain no word for "content I do not have yet," and G2.3 lints at zero violations for an eighth noun. Either the concept hides completely inside `remote`, or one of the two gates must move.
4. **Lattice's differentiator is a local query in a world where review is a forge.** Git's SHA-256 story shows that a complete, correct, published design can sit unshipped for nine years because forges have not moved. Lattice's non-goals rule out a hosting platform, so `ltx trace --agent --unreviewed` is a laptop-local answer to a question teams ask in pull requests. The provenance layer's value is bounded by adoption Lattice has explicitly declined to build.
5. **A resident watcher is now table stakes, and its Linux failure mode is a shared kernel ceiling.** Lattice's watcher will consume one inotify watch per directory exactly as Git's does. On a monorepo this can exceed `fs.inotify.max_user_watches` and force the same bankruptcy-and-rescan path. Nothing in G1.5 currently measures behaviour at watch exhaustion.
6. **Git is closing the ergonomics half of pillar 2.** `git history reword|split|fixup` is a rewrite, so lenses remain substantively different — but the honest comparison for lenses is now `git history`, not `git rebase -i`, and the marketing claim "Git's clean history requires destroying the record" must be paired with the observation that Git made destroying it much more pleasant in 2026.
7. **Claims about Git's limits decay within one release.** The `--path-walk`/`--filter` incompatibility was real in 2.50.1 and gone in 2.55. Any Lattice-facing document that asserts a Git shortcoming without a version pin will be wrong within a year, and G0-gate documents are the ones most likely to be quoted back.

### Where a stated target looks unrealistic

- **G1.5's <100 ms.** Against published numbers for the same *class* of mechanism (resident watcher plus untracked cache) at 750–830 ms on 400K–2M-file trees, sub-100 ms is roughly an 8x claim. It will be decided entirely by the reference repo's file count — which the gate does not publish. If the reference repo is ~50K files, Git will also clear it and the gate proves nothing.
- **G5.8's ≤25%.** Not a differentiating threshold; blobless clone already clears it.
- **G3.3's zero anomalies.** Achievable against Git 2.50.1, not durable against Git 3.0 or against `git history`-produced commits unless the corpus is widened now.
