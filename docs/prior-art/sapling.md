# Sapling (Meta)

> Sapling is Meta's source control system: a heavily evolved fork of Mercurial, open-sourced 15 November 2022. Work began around 2012 — the launch post's author marks it as "my 10th year of working on Sapling at Meta, almost to the day," and the January 2014 "Scaling Mercurial at Facebook" post already claims "over 500 patches to Mercurial over the last year and a half." That post explains the fork choice: Mercurial was "written mostly in clean, modular Python (with some native code for hot paths), making it deeply extensible," whereas "Git's internals would be difficult to work with for an ambitious scaling project." Sapling ships as three components: the `sl` client (GPL-2.0; GitHub reports the repo's primary language as Rust, though the client is a Python/Rust hybrid and the undo path is still Python); Mononoke, the Rust server that has been "the production back end for our monorepo since 2019"; and EdenFS, the virtual filesystem. **Only the client is publicly supported.** As of 2026-09-03 the GitHub API reports 7,002 stars, 396 forks, last push that same day — actively developed, not abandoned. Sapling is not a failure. It is the best-tested friendly porcelain in existence, and its authors state exactly which world it was tuned for: "Some of the design decisions are geared towards corporate, always-online, single-master, rebase-instead-of-merge, monorepo environments."

## 1. What did it get right?

### 1.1 Undo as a reference-state restore, not an inverse patch

`eden/scm/sapling/ext/undo.py` (1,479 lines, and live — `undo=` appears in the extensions block of the builtin production config in `eden/scm/lib/config/loader/src/builtin_static/production.rs`) wraps command dispatch. Before every mutating command it writes the **pre-image** of a small set of named references into `.sl/undolog/`, a directory of revlogs: `index.i` (one entry per command, mapping name → node hash) plus `bookmarks.i`, `workingparent.i`, `visibleheads.i`, `command.i`, `date.i`. `sl undo` computes a reverse index into `index.i`, reads that entry's nodedict, and restores three things: bookmarks (remove all current, apply recorded), the working-copy parent (`hg.clean`, or `dirstate.rebuild` under `--keep`), and visibility (`_restoreheads` → `changelog._visibleheads.setvisibleheads`).

The consequence is what Lattice wants: undoing a rebase applies **zero patches**. Pre-rebase commits were never deleted, only made invisible, so undo is a set-assignment on the visible-head set. This works because Sapling inverted Mercurial's visibility model — "Sapling treats all commits as invisible by default, using 'visible heads' and bookmark references to mark commits and their ancestors as visible."

Two weak joints, both instructive. First, `sl redo` walks backwards through `index.i` looking for entries whose recorded argv has `commandlist[0] == "undo"`, then **re-parses that recorded argv** with `cliparser.parsecommand(commandlist, cmdtable["undo"][1] + commands.globalopts)` to recover `--step`. Position lives in one file, `undolog/redonode`; a `undolog/gap` file marks stretches where logging was absent, and undo refuses to cross them ("unknown command(s) run, gap in log"). It is a linear list with a cursor, not a DAG of operations. Second, there is no pruning — and the only path that ever shrinks the log is catastrophic: on a revlog/`mpatch` error, `_nukerevlogs` calls `localvfs.rmtree("undolog")` and recreates the directory empty, destroying all undo history to recover from corruption in one record.

### 1.2 MetaLog: a content-addressed DAG of repo metadata

Separately from the undolog, Sapling stores mutable repo references in **MetaLog** (`eden/scm/lib/metalog`, a live Rust crate), structurally a tiny Git: "A blob store backed by ZStore. Blobs are keyed by their content SHA1s. There are 2 kinds of blobs: root, and content." A root blob contains "A description of why this root was created. A map from (file) names to keys of content blobs. Keys of parent roots." Changes "are buffered in memory until an explicit flush to disk"; on concurrent write, "If MetaLog notices that the latest root is changed on disk, it will attempt to perform a merge defined using a merge function specified by the application. A merge failure will prevent MetaLog from committing the changes to disk." Ordering rule: "Write MetaLog last. MetaLog tracks references to other data."

This is the cleanest published design for "atomic multi-reference update plus a recorded reason," and a direct template for Lattice's operation log. The honest wrinkle: Sapling carries **two** overlapping metadata histories — MetaLog (Rust, content-addressed, atomic, merge-capable) and the older `undolog` (Python revlogs, linear, unprunable) — and user-facing `sl undo` uses the latter. The better design shipped, and the user-facing feature was not moved onto it.

### 1.3 Smartlog: legibility by subtraction

`sl` with no arguments prints your not-yet-pushed commits, where you are (`@`), important remote bookmarks, the graph relation between them, and commits that are "old and have been landed, rebased, amended" (marked `x`, annotated "Landed as YYY"). It gives "a succinct view of your work by hiding all commits that aren't relevant to you"; "the dashed line on the left represents the main branch and elides thousands of commits." The insight is not the rendering — it is that the *default* view is a filtered projection, and the unfiltered graph requires a different command. Sapling can afford this because of the segmented changelog (§1.6): "commands like smartlog are less than a second, regardless of how big the repository is."

### 1.4 Mutation records + stable stacks

Rewrites (`amend`, `rebase`, `fold`, `split`) record a **mutation** from predecessor to successor; "mutation uses IndexedLog for `O(log N)` lookup." Crucially, "Mutation does not decide visibility" — unlike Mercurial's obsstore the two concerns are separated, and "If all successors of a mutation are invisible, then the mutation is ignored. This means mutation can be implicitly tracked by visibility. Restoring visibility to a previous state during an undo operation effectively restores the commit rewrite state." That is why §1.1's undo can restore rewrite state without touching mutation records. Amending mid-stack auto-restacks descendants. Edward Yang's March 2026 write-up on running parallel AI agents against Sapling singles this out: "I feel Sapling's tracking of successors is important for a good stack flow," having found the Git-side alternative wanting — "I found branchless buggy and failed to reliably restack commits."

There is a cost the docs state plainly: obsolescence data "can grow over time unbounded while bookmarks and visible heads can shrink using commands like `sl bookmark -d` and `sl hide`. Practically, we assume a bounded number of bookmarks and visible heads." The speed of the whole visibility model rests on that bound.

### 1.5 `absorb` and linelog: assignment without merge

`sl absorb` maps each uncommitted changed line to the commit in your stack that last touched it and amends it there. The engine is **linelog**, "an implementation of interleaved deltas" that "provides conflict-free stack editing ability," expressed as bytecode with five mnemonics (`JGE`, `J`, `JL`, `LINE`, `END`) over a 2-bit opcode — `J` and `JGE` share one, since "`J Addr` is just `JGE 0 Addr`" — with operand 1 at 30 bits and operand 2 at 32 bits. Checkout means setting a register and executing; annotate falls out of the same pass because `LINE` carries the introducing revision. `absorb` edits history via `replace_lines(brev, a1, a2, b1, b2)`.

Two properties matter to Lattice. First, "Absorb does not write to the working copy" — the rewrite is in memory, so builds do not invalidate. Second, it **cannot conflict**: it follows line provenance rather than performing a 3-way merge, and "If absorb cannot find an unambiguous commit to amend for a change, that change will be left in the working copy, untouched." Its scope is bounded — "Commits outside the revset `. % (public() | merge() | immutable)` will not be changed" — and linelog itself "assumes linear history. The revision comparisons are done using direct integer comparisons."

### 1.6 Segmented changelog

Per Meta's launch post, the segmented changelog "allows the downloading of the high-level shape of the commit graph from the server, taking just a few megabytes," and "enables querying the graph relationship between any two commits in O(number-of-merges) time, with nothing but the segments and the position of the two commits in the segments." Further: "When running log or blame on a file, we're able to bisect the segment graph to find the history in O(log n) time, instead of O(n), even in Git repositories." (These claims live in the 2022 engineering post, not in the `sapling-scm.com` scale pages, which mention segmented changelog only in a timeline.)

### 1.7 ISL and optimistic state

ISL is a React 19 + Jotai front end talking to `isl-server` over a WebSocket that is explicitly token-gated ("Only the websocket is sensitive and requires the token"); the server shells out to `sl`. It also ships as a VS Code webview and as a platform target named `agentHome` (`addons/isl/agentHome.html`, `src/platform/agentHome.ts`, `addons/isl-server/platform/agentHomeServerPlatform.ts`) — a browser-like ISL embedded in a host window that drives its theme via a `?theme=` URL param. *(That this host is specifically an AI-agent product is inference from the name and shape; the code does not say so.)*

Its best idea is **optimistic state appliers**: each `Operation` supplies pure transforms — `optimisticDag(dag)` / `previewDag(dag)` on the commit DAG, plus `makeOptimisticUncommittedChangesApplier` and `makeOptimisticMergeConflictsApplier` — predicting the command's result so the UI shows the future immediately while commands queue. Three flags (`hasCompletedOptimisticState`, `hasCompletedUncommittedChangesOptimisticState`, `hasCompletedMergeConflictsOptimisticState`) track reconciliation, and the code carries an explicit escape hatch: "It's possible for optimistic state to be incorrect, e.g. if some assumption about a command is incorrect in an edge case but the command doesn't exit non-zero. This provides a backdoor to clear out all ongoing optimistic state from *previous* commands."

### 1.8 Commit Cloud, EdenFS, and a shipped redaction protocol

Commit Cloud uploads every draft commit as it is created, so "sharing code is as simple as sending your colleague a commit hash and having them run `sl goto HASH`." EdenFS materializes working-directory files on demand: "On Linux, EdenFS uses FUSE"; "On macOS, EdenFS uses NFSv3"; "On Windows, EdenFS uses Microsoft's Projected File System."

Most relevant to Lattice: **Mononoke ships a redaction protocol.** A `RedactedBlobstore` decorator sits near the top of the blobstore stack and intercepts every access; keys are Blake2b **content IDs**, so "Renaming or moving a file does not bypass redaction." Each redaction set carries a `reason` (task or SEV) and an `enforce` boolean — `false` means log-only. Config reloads from Configerator every 60 seconds; all access attempts are logged to Scuba with session ID and username. The commit graph is never modified.

Its documented limits are the interesting part, and there are four, not one. Metadata is **not** redacted: "Commit messages, file paths, author information, and other metadata remain visible. If metadata itself contains sensitive information, redaction alone is insufficient." Caches persist: "copies may exist in caches (memcache, cachelib, local filesystems)… immediate removal is not guaranteed." Derived data leaks references: "Some derived data types (like Git trees or Mercurial manifests) may reference redacted content IDs." And, decisively, **nothing is deleted**: "Redaction prevents access but does not delete content from the blobstore. The blobs remain stored and continue consuming storage space." Also: "There is no mechanism to selectively grant access to redacted content based on user identity," and configuration changes take up to 60 seconds to propagate, during which "some servers may enforce redaction while others do not."

## 2. Why didn't it win (or why is it niche)?

Sapling won decisively at Meta and is not in decline — the repo was pushed the day this was written. It has not spread, for reasons that are overwhelmingly **ecosystem, not technical**.

**The magic is server-gated, and the server is not shipped.** The README says of both Mononoke and EdenFS: "Not yet supported publicly, OSS is buildable for unsupported experimentation." This is enforced in code, not only in docs: `eden/scm/sapling/ext/commitcloud/gitservice.py` — a 50-line class whose docstring reads "Remote commit-cloud service for git repos" — raises `error.GitUnsupportedError` for `getsmartlogbyversion`, `updatecheckoutlocations`, `updateworkspacearchive` and `renameworkspace`, and bare `NotImplementedError` for `shareworkspace`, `rollbackworkspace` and `cleanupworkspace` (those three carry comments referencing test-environment gaps, so read the first four as the load-bearing set). A GitHub user gets the porcelain and materially less of the durability; the same holds for EdenFS, lazy segmented-changelog fetch, and server-side pushrebase.

**Git interop forces a mode split with real hazards.** In `.git` mode `git` and `sl` coexist, but "Mixing `sl` and `git` commands might not work in all cases" — an interrupted `sl rebase` needs `sl rebase --continue`, not Git's; `sl` "might put the repo in a 'detached head' state," and you must `git branch some_name` before checking out away "to avoid losing commits." `sl goto` runs `git checkout` under the hood, but "Other `sl` commands like `commit` or `diff` do not respect `.gitattributes`" (so LFS is partial); local tags are unsupported; submodules are not fully supported. `.sl` mode gets EdenFS, lazy graph protocols and custom storage — and lists Git commands as **"Not supported."** You cannot have both.

**It was open-sourced late, into a contested window.** By November 2022 the same ideas — revsets, stacks, undo, evolution — were reaching people through jj and git-branchless. As of 2026-09-03 the GitHub API reports jj-vcs/jj at 31,350 stars against Sapling's 7,002 — roughly 4.5× — despite Sapling's head start and better GUI. On the "Ask HN: Git Alternatives – Sapling vs. Jj" thread, a jj contributor writes: "isl is an incredible tool, it is easy to use even for newcomers, and I consider it a major advantage over Jujutsu!" It was not enough.

**It is Meta-shaped, and says so.** The October 2025 "Branching in a Sapling Monorepo" post shows the cost concretely: full-repo merges "create merge commits with multiple parents, making the commit graph *wide* (high branching factor) and *non-linear*," and "In large monorepos, this creates performance problems for operations like `sl log` and `sl blame`" — segmented-changelog queries being O(merges). Meta therefore built *directory branching* (`sl subtree copy` / `graft` / `merge`) to keep "most commits have a single parent." A system optimized around one always-reachable trunk is a hard sell to a world of forks and PRs.

**Binaries block adoption independently.** Sapling routes 10 MB–2 GB files to "a special server that speaks the Git LFS protocol," and "Files larger than 2GB are currently not battle-tested in Sapling, though they may still work." On HN this lands exactly as you would expect — "Sadly, $work uses git LFS, so neither is a possibility for me," and separately "The only major limitation for me is git-lfs support so for certain repos I have to revert to git."

## 3. What will Lattice do differently, concretely?

**3.1 Working-copy-restoring undo is table stakes, not a differentiator — gate it as parity.** The draft version of this section claimed Sapling's exclusion as Lattice's opening. That is only true against Sapling. jj's own comparison page states: "Thanks to jj snapshotting the working copy, it's possible to undo changes to the working copy. For example, if you `jj undo` a `jj commit`, `jj diff` will show the same changes as before `jj commit`, but if you `sl undo` a `sl commit`, the working copy will be clean." So Lattice's continuous autosnapshot buys parity with jj, not an advance on the field. Ship it, but do not sell it. Concretely: every `ltx-oplog` operation record carries a `pre` field holding three root hashes — autosnapshot root, checkpoint-DAG root, ref-set root. Gate **G1.3**: over 100,000 generated operation sequences drawn from the full verb set, `ltx undo` after every prefix restores a state whose recomputed roots equal the recorded `pre` triple, with zero patch applications on the undo path, and — unlike Sapling, where `cmdutil.bailifchanged(repo)` guards three call sites in `undo.py` — with no refusal on a dirty working state.

**3.2 No argv re-parsing, no linear cursor — and thinning that is not `rmtree`.** Sapling recovers `--step` by re-parsing recorded argv, and its history is a list with a `redonode` cursor and a `gap` sentinel. Lattice's op log is a Merkle-linked DAG: each record stores structured arguments plus the parent operation hash, so undo-of-undo is a parent-pointer move. Gate **G1.4**: no code path in the `ltx-oplog` undo subsystem may reference the CLI argument parser; enforced by a crate-level lint (deny-list on the `ltx-cli` parser symbols from `ltx-oplog`). Gate **G1.6**: op-log thinning exists, each thinning event is itself an appended operation record, thinning may never remove a record that is the `pre`-image of a reachable checkpoint, and corruption recovery is per-record — a single bad record must be quarantined and skipped, never trigger Sapling's `_nukerevlogs` behaviour of `rmtree`-ing the whole log.

**3.3 Close the gap hole at the type level, not by convention.** Sapling's `gap` file exists because `safelog` acquires `undolog/lock` with `timeout=2` and, on `error.LockHeld`, logs "undolog lock timeout" to Scuba and lets the command proceed unlogged. That is universal undo silently becoming non-universal. Gate **G1.5**: the `ltx-store` mutation API is private and reachable only through an `ltx-oplog::OpTransaction` handle, so no repo mutation can commit without its operation record; verified by crash-injection tests (kill at N points across the write path) asserting zero orphan mutations — a store state with no corresponding op-log record is a hard failure, not a gap marker.

**3.4 Content-defined chunking must beat the *strong* baseline, not a strawman.** Mononoke's file storage takes `FilestoreParams { chunk_size: u64, concurrency: usize }` — **fixed-size** chunking, and only "chunked for large files." Dedup then comes from whole-file Blake2b content IDs plus Packblob, which "uses Zstd compression with delta compression. One blob serves as a dictionary, and other blobs in the pack are compressed using deltas against that dictionary." Gate **G2.1** must therefore hold delta compression *constant*: corpus of large binaries mutated by head-insertion, comparing Lattice FastCDC-over-all-content + zstd against fixed-size chunking + zstd dictionary/delta. Requirement: ≥2× reduction in stored bytes on head-insertion mutation. Comparing CDC against fixed chunking *without* delta compression would guarantee a win and prove nothing. If the gate fails, the all-content-CDC decision reverts to CDC above a size threshold with whole-file addressing below it.

**3.5 `ltx assign` inherits absorb's contract, and its scope limit.** Two properties are the whole value: it never conflicts (line provenance, not 3-way merge) and it never writes to working state. **ADR-014** fixes both as invariants, plus absorb's refusal semantics — anything ambiguous is left in working state, untouched, and reported — so `ltx assign` cannot later be "improved" into something that merges. ADR-014 must also state the scope limit explicitly, because linelog "assumes linear history" and absorb stops at merges and public commits: v1 `ltx assign` operates only over a linear checkpoint run with no conflict objects, and refuses (loudly, with the reason) otherwise.

**3.6 Lenses subsume ISL's optimistic previews.** ISL's appliers are already lenses: pure `Dag → Dag` transforms over real state. **ADR-015** unifies them — a speculative lens takes the pending operation as a parameter and projects the post-operation checkpoint DAG — so Lattice has one projection mechanism, not two. Carry ISL's escape hatch across as `ltx lens --reset`, dropping all speculative projections, because ISL's own comment concedes optimistic state can be wrong while the command still exits zero.

**3.7 The Git bridge picks a mode, names it, and gets its own gates.** Sapling's `.git`/`.sl` split is the empirical result of trying to do both, and `.sl` mode — the one with the storage and scale wins — lists Git commands as unsupported. `ltx adopt` defaults to the `.git`-equivalent mode, and its command documentation must publish the concrete unsafe-concurrency list, using Sapling's caveats as the starting checklist, not a hypothesis: interrupted rebase/merge state, detached HEAD, LFS, `.gitattributes`, local tags, submodules. Treat bidirectional lens-defined Git publication as a multi-quarter subsystem with its own gate series, not a prerequisite checkbox.

**3.8 Provenance is the actually-open ground — ship the index, not the porcelain.** Sapling has no actor-class model, no tool/model identity, no task linkage, no self-assessment, no queryable provenance index. Signing is a Git-only pass-through: "Currently, signing is only supported with commits in Git repos," and "There is no `-S` option for `sl commit` or other commands, as signing is expected to be set for the repository" — with per-action disabling via `--config gpg.enabled=false` documented as something that "has not been heavily tested." Nothing in Sapling answers `ltx trace --agent --unreviewed --touching src/auth/`. Gate **G3.1** makes that literal string the acceptance case, with a latency bound on a synthetic repo of ≥1M checkpoints. Meanwhile the `agentHome` ISL surface is competitive pressure on the *interface*, not on the record — which is the argument for shipping the index early.

### Residual risk for Lattice

- **The parallel-agent practitioner report argues against Lattice's working-copy model.** Yang, running parallel agents on stacks, rejects jj for precisely the behaviour Lattice adopts: "Jujutsu will transparently update worktrees when a separate worktree is amended? This seems bad: I want to delay worktree updates until I am ready (e.g., the agent finishes work.)" Lattice pairs continuous autosnapshot with a `workspace` noun. The single published report on the flagship use case says the winning property is *deferred, explicit* propagation between workspaces. Autosnapshot must be workspace-local by default, and cross-workspace propagation must be pull-triggered — this needs an ADR before the workspace semantics freeze.
- **Undo of a sync is not locally decidable.** Sapling scoped undo to local effects deliberately: "For hybrid commands that result in both local and remote changes, `sl undo` will undo the local changes, but not the remote changes." Neither Sapling nor jj can un-send a push; the bytes are gone. Lattice's "`ltx undo` undoes everything, including… syncs" is only truthful if defined as *local state restore plus an emitted signed retraction*. Merge the two definitions in the spec text or the claim is false.
- **Local-first redaction and Mononoke's fail on opposite axes; neither is GDPR erasure.** Mononoke enforces because it is the chokepoint — but "Redaction prevents access but does not delete content from the blobstore." Lattice deletes locally but has no chokepoint: peers already hold full copies, so a tombstone is a request. Mononoke = enforcement without deletion; Lattice = deletion without enforcement. Neither alone satisfies an erasure obligation, and the docs must say which one Lattice is.
- **Redaction targets the wrong bytes for the case that motivated it.** Mononoke: "Commit messages, file paths, author information, and other metadata remain visible." Lattice's provenance — actor identity, transcript hashes and pointers, task URLs — is exactly metadata and exactly the GDPR-relevant surface. The tombstone must cover provenance fields, or the agent layer becomes the compliance liability the redaction protocol was built to remove.
- **Derived indexes retain redacted content.** Mononoke concedes derived data "may reference redacted content IDs." Lattice has two derived stores — the tree-sitter semantic index and the provenance index — and "regenerable" is not the same as "purged." The redaction protocol must enumerate every derived index and invalidate it as part of the tombstone operation, logged in the op log.
- **First-class merges collide with fast history queries and with bounded head sets.** Ancestry is O(number-of-merges), and Meta declined full-repo branching for that reason. Lattice's never-blocking merges with conflicts as checkpoint contents generate strictly more merge nodes than a rebase workflow. Separately, Sapling's visibility speed rests on an assumption Lattice may break: "Practically, we assume a bounded number of bookmarks and visible heads." Gate **G4.1**: benchmark `ltx log` / `ltx blame` against a synthetic high-merge-density DAG, and gate **G4.2**: measure head/anchor-set growth under sustained never-blocking merges — both before the checkpoint format is frozen.

### Where the spec looks unrealistic

- **"Seven user-facing nouns, total" is already violated by the spec itself.** *Conflict* is described as a first-class object users interact with, and *changeset* as a named unit of the working diff — that is nine. Worse, *change* versus *changeset* is a near-homonym pair with different meanings, which will need a glossary entry; needing a glossary entry to separate two nouns is the tell that one of them is doing too much work. Fold changesets into changes, or amend the count and stop quoting it.
- **Excellent porcelain is demonstrably insufficient.** Sapling has the best undo, the best stacked-commit GUI, shipped four years ago, and is outstarred 4.5× by a tool whose own community concedes ISL is "a major advantage." A UX-quality thesis alone moves no one. The defensible ground is the signed, indexed, queryable provenance record.
- **"Git bridge ships first" plus "plain-Git teammates notice nothing" is the harder half.** Sapling, with Meta's resources and a decade of Mercurial interop experience, still labels this "Git support may have some remaining kinks to be worked out" — and could not deliver both modes at once.
