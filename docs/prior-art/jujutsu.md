# Jujutsu (jj)

> Jujutsu is a Git-compatible version control system that Martin von Zweigbergk "started as a hobby project in late 2019," and which "evolved into my full-time project at Google" — though the README is explicit that "this is not a supported Google product." The `jj-vcs/jj` repository was created 2020-12-18; retrieved 2026-09-03 the GitHub API reports 31,350 stars, 1,195 forks, 368 contributors, and 811 open issues (the API's `open_issues_count` of 1,222 counts pull requests too — the draft figure this analysis replaces). Latest release `v0.44.0`, published 2026-08-06. Still pre-1.0, with backward-incompatible on-disk format changes promised before then. jj is Lattice's closest living relative: working-copy-as-commit, stable change IDs, an operation log with universal undo, first-class conflicts, and a Git bridge as the production path. On 2026-09-01 von Zweigbergk was named CTO of East River Source Control (Amplify Partners-backed). That is not the whole of it: `docs/paid_contributors.md` now lists ERSC **first**, ahead of Alphabet/Google, with eight named jj contributors — martinvonz, ilyagr, thoughtpolice, steveklabnik, benbrittain, davidbarsky, ConnerPetzold, bts. A funded company has absorbed a large fraction of jj's core, and its stated mission is "creating the building blocks for human ↔ machine collaboration." That is Lattice's thesis sentence, with a balance sheet behind it.

## 1. What did it get right?

jj's central insight is not any single feature but a substitution: it reuses Git's own commit/tree shape one level up, to describe the *repository* rather than the *tree*. Everything Lattice admires about jj — undo that cannot fail, lock-free concurrency, conflicts that do not compound, a change identity that survives amendment — falls out of that one move plus a small algebra. The pieces below are worth adopting because they are cheap consequences of a good representation, not because they are clever engineering bolted onto a bad one. Where jj pays a price for a design, that is noted here rather than deferred to §2.

### 1.1 The operation log is a DAG of typed objects, not a reflog

Per `docs/technical/concurrency.md`, the analogy is exact: "each commit object is instead an 'operation' and each tree object is instead a 'view'." A **view** holds the complete repo state — visible head commits, bookmarks, tags, Git-ref positions in Git-backed repos, and the working-copy commit in each workspace. An **operation** holds a pointer to its view, pointers to its parent operation(s), and metadata (timestamps, username, hostname, description). Both are defined in `op_store.proto`.

Because a view *completely* defines repo state, undo is a move to a different view — not an inverse patch, not a revert commit, not a replay. `jj undo` steps back one operation; `jj op revert` reverts a specific non-latest operation; `jj op restore` restores the whole repo to an earlier view; `--at-op` loads the repo at any operation for read-only forensics and explicitly skips working-copy snapshotting while doing so.

### 1.2 Lock-free concurrency falls out of the same structure

A command loads the repo at the latest operation and is thereafter immune to concurrent writers; on completion it writes a new operation with the load-time operation as parent. When jj later finds multiple heads, it performs a **3-way merge of the view objects against their common ancestor**. Divergent bookmark moves are not an error — they become a conflicted ref, surfaced as `??`. The docs are honest about the limits: this holds only on filesystems that guarantee a write is visible only once previous writes are, Git-backend corruption is still possible, and concurrent modification across machines "might lose bookmark pointers" though commits remain safe.

### 1.3 Change ID is a *property of a commit*, not an object

The glossary is verbatim and frequently misquoted: "Changes themselves don't exist as an object in the data model; only the change ID does. The change ID is a property of a commit." Change IDs are typically 16 bytes, rendered as 12 letters in the k–z range — "hexadecimal numbers that use 'digits' z-k instead of 0-9a-f" — so they are visually unmistakable from commit IDs, which are 20 bytes under the Git backend and identical to Git's.

Storage is a sidecar: change IDs and predecessor lists live in a `StackedTable` under `.jj/repo/store/extra/`, a bespoke format chosen because jj wanted lock-free concurrency and found no existing KV store that offered it. Parent tables are kept at least 2× the size of their children, giving O(log N) amortized insertion and lookup. For commits created by Git, jj synthesizes an empty predecessor list and the **bit-reversed commit ID** as change ID. Since v0.30.0 jj additionally writes a non-standard `change-id` Git commit header (`git.write-change-id-header`). The predecessor chain powers `jj evolog` — the amendment audit trail Git's reflog only approximates. One caveat Lattice should read closely: "There's no garbage collection of unreachable tables yet." jj's identity sidecar grows monotonically.

### 1.4 Conflicts are an algebra, not a mode

From `docs/technical/conflicts.md`: a conflict is "an ordered list of tree objects linked from the commit (instead of the usual single tree per commit). There will always be an odd number of trees." Trees A,B,C,D,E denote `A+(C-B)+(E-D)`; a plain 3-way merge is `A+(C-B)`. Contents are computed on demand; merging recurses into a subtree only when tree-ID comparison cannot resolve it trivially, then into hunks only when the file ID cannot.

The payoff is `Merge::flatten()` and `Merge::simplify()` in `lib/src/merge.rs`. Rebasing a commit carrying conflict `C+(B-A)` onto D yields `D+((C+(B-A))-C)`, which simplifies to `D+(B-A)` — a plain 3-way merge, no trace of C. Reverting conflicted `E=C+(B-A)` yields `E+(C-E)`, which simplifies to `C`. Conflicts therefore do not compound under repeated rebase, which is the actual reason "merges never block" is survivable rather than a slow-motion disaster.

### 1.5 The Git backend is an escape hatch with a documented seam

`GitBackend` (on gitoxide) is the only production-ready commit backend; `SimpleBackend` "is just a proof of concept." Colocation is the default for `jj git init`/`jj git clone` (disable with `--no-colocate` or `git.colocate = false`); `.jj` and `.git` share one working copy and jj imports/exports on every command. Crucially, **mutating `git` commands are undoable**: they appear in `jj op log` as an "import git refs" operation and are reachable by `jj undo`/`jj op restore`. To stop Git's GC eating jj-only commits, `GitBackend` writes a ref per op-log commit under `refs/jj/keep/`. Conflicts, unrepresentable in Git, live authoritatively in a non-standard `jj:trees` commit header, with `.jjconflict-base-*/` and `.jjconflict-side-*/` root directories existing only so the trees stay reachable. Unsupported: LFS, submodules, partial clones, `.gitattributes`, hooks, `git-worktree`.

### 1.6 Revsets, reused as policy

Revsets are a functional query language over commits (`x-`, `x+`, `x::y`, `x..y`, `~`, `&`, `|`, plus `heads()`, `roots()`, `fork_point()`, `files()`, `author()`, `conflicts()`, and `exact:`/`glob:`/`regex:`/`substring:` patterns). `docs/technical/revset-evaluation.md` names five stages: Parsing and Alias Expansion, Symbol Resolution, Optimization (eleven recursive rewriting passes), Visibility Resolution into a `ResolvedExpression`, and Evaluation by Index. The same language is then reused as *policy*: `revset-aliases."immutable_heads()"` defines what may not be rewritten, defaulting to `builtin_immutable_heads()` = `trunk() | tags() | untracked_remote_bookmarks() | untracked_remote_tags()`, with ancestors also immutable and `--ignore-immutable` as the override. Reusing the query language as the safety predicate is an excellent, cheap idea Lattice should copy outright. Workspaces (`jj workspace add`) give each working copy its own working-copy commit against one shared repo.

## 2. Why didn't it win (or why is it niche)?

jj is not in decline; it is on a steep, genuine ascent, and it is still niche. Both are true. The reasons are less about the model — which is better than Git's — than about the three things a model cannot fix by itself: the cost of a working-copy scan, the forge's definition of a reviewable unit, and the size of the vocabulary a user must hold. Each is documented in jj's own tracker with dates and numbers, and each maps onto a Lattice gate.

**The performance tax is real, old, and only partly a snapshot problem.** Issue #1841 has been open since 2023-07-10 with 57 comments. The reporter measured `jj init --git-repo=.` at 4m59s and `jj status` at 25s on a 3M-LOC repo with hundreds of thousands of commits, 112,625 tags and 4,540 branches, against `git status` at "a second or two." Progress is real: `--ignore-working-copy` was 263.8ms even then, and a non-colocated worktree cut status to ~9s. But three later datapoints matter more to Lattice than the headline. (a) In August 2023 arxanas profiled `jj status` on nixpkgs *with Watchman* at 768ms — snapshot 257ms, conflicts 424ms — and concluded "I think we could get `status` down to an acceptable ~100ms." (b) In March 2025 qfel measured `jj st` at 1.207s on a *fresh clone* of `zed`. (c) In October 2025 Vampire measured `jj log` at 2.8s on JetBrains/kotlin (~55k Git refs + ~44k jj refs) and reported that "Enabling `watchman` did not really change the timing" — `git pack-refs` helped more. The cost there is ref/index import, not the filesystem scan, and a resident watcher does not touch it. `fsmonitor.backend` defaults to `None` in `lib/src/fsmonitor.rs`; Watchman is opt-in and must be installed separately.

**The 2025 network fix was not a snapshot fix.** `git.subprocess = true` cut one user's fetch from 38.070s to 8.889s and push from 1:25.79 to 22.600s on a ~300k-commit repo (alexpls, 2025-02-11) — but that user had `core.fsmonitor = watchman` enabled in *both* columns. It replaced libgit2 on network paths. The working-copy cost was untouched.

**Large binaries are unsolved.** `snapshot.max-new-file-size` defaults to 1 MiB "as an anti-footgun measure" — and applies only to *new* files; files already in the working copy are exempt. Git LFS is unsupported. Issue #2865 ("FR: Support large binary files better than Git"), which cites the FastCDC paper directly, has been open since 2024-01-22 with 13 comments and no implementation. The roadmap's entire commitment is one sentence: "We have talked about somehow using content-defined chunking (CDC)… Maybe we will store files in our future cloud-based server using the same model as XetHub."

**Lock-freedom has a scoped hole.** #2193 (open since 2023-09-01) is narrower than it is usually quoted: with the Git backend, the change-ID index relies on locks that "would not be available if the repo was synced with `rsync` or over Dropbox." In that case the index can be corrupted — `jj co revisionid` wrongly reports no such revision — with `jj debug reindex` as recovery. It is not a general local-repo hazard; it is a distributed-filesystem hazard, which is exactly the configuration jj's concurrency design advertises as supported.

**The forge is the real gatekeeper.** jj's model presumes history is cheap to reshape; GitHub's presumes the reviewed unit is a pushed commit whose identity must not change. jj ships `immutable_heads()`, but the default set covers *untracked* remote bookmarks (added in 0.20.0 via #4083) — which is precisely how discussion #4285 ("An unintentional force push," 2024-08-15) happened to a first-day user who had already read the immutability docs but had a local bookmark tracking the remote. Leakage runs the other way too: #9571 (2026-05-28) documents conflict commits reaching the real Ghostty repository because plain `git` bypassed jj's checks, and names "AI agents" as a likely vector. #9707 (2026-06-26, still zero comments) asks for destructive writes to shared state to be a distinct operation class at all. The forge boundary is where jj's elegance stops.

**`jj undo` stops at the network.** A push is an ordinary operation and *is* undoable — but per jj's own teaching material, "It doesn't tell the remote to restore its previous state, the remote is left intact," producing conflicted bookmarks and divergent change IDs on the next fetch or push. It adds: "In the future, `jj undo` may outright refuse to undo operations that interacted with the remote."

**Vocabulary drift.** jj started minimalist and accreted: change, commit, revision, operation, view, workspace, bookmark, conflict, divergent change, hidden commit, change offset, evolog, revset, fileset, template, immutable set. #4285's author — a fan — wrote that "the documentation uses the terms 'changes' and 'commits' inconsistently." The FAQ's very first entry is "Why does my bookmark not move to the new commit after `jj new/commit`?"

**Adoption, honestly stated.** A JJ Con 2025 keynote summary reports **~900 internal Google users**; the conference was held 2025-09-28 in Sunnyvale, and I could not reach the primary talk, so treat the figure as unconfirmed secondary. If it is right, then roughly six years after a late-2019 start, with the creator full-time inside the most VCS-sophisticated company on earth and invisible Git interop as the adoption ramp, jj had ~900 internal users. The roadmap explains part of the shape: "Most people contributing to Jujutsu do so in their spare time, which means that we cannot attach any target dates to any of the goals below." That constraint has now been lifted for jj — by a company — and not for Lattice.

## 3. What will Lattice do differently, concretely?

Lattice takes jj's representation and refuses three of its concessions: that undo may quietly stop at the network boundary, that automatic conflict resolution may be lossy without a record, and that storage efficiency may remain a roadmap sentence. Each refusal below names the data structure it changes and the gate that falsifies it — G1.2, G1.3, G1.4, G1.8, G1.9, G2.7, G2.8, G3.2, G3.3, G3.6, G5.1, G5.2, G5.4 — plus ADR-1 (merge model), ADR-2 (chunk parameters) and ADR-3 (store backend), which must land under G0.6 before the corresponding subsystem is built. Where jj's evidence says a gate is optimistic, that is recorded below rather than argued away.

**3.1 Op-log records span both endpoints and are typed by blast radius.** jj's operation points only to *its own* view. Lattice's `OpRecord` stores `pre_root` alongside `post_root`, `parents[]`, and a `class` field partitioning operations into `local`, `shared-append`, and `shared-destructive`. Undo of a `local` or `shared-append` operation is a root-pointer move, falsified by **G1.3** (HARD, 0 failures over ≥100k in-process and ≥1000 CLI property-generated sequences, coverage-gated). A `shared-destructive` operation is never silently undone: `ltx undo` refuses and offers a signed retraction, itself a new logged operation. This is the design jj #9707 requested and has not received.

**3.2 Change-ID survival across the bridge is a measured number, not a hope.** jj's `change-id` header survives `git commit --amend` and explicitly does not survive `git rebase`. Lattice therefore cannot rely on the header alone: `ltx sync` maintains a bridge anchor table keyed `git-commit-id → change-id`, reconciled on every fetch, with content-similarity re-anchoring when a plain-Git teammate strips the header. **G3.2** (SOFT, ≥99%) measures change-ID *and provenance* recovery across ≥500 simulated PR flows; **G3.3** (HARD, 0) requires zero observable anomalies in the Git-only teammate suite. Anything the re-anchoring heuristic cannot recover is a logged lossy edge under **G3.4**, not a silent miss.

**3.3 Keep jj's conflict algebra; refuse its silent lossiness — and note where it actually bites.** Lattice adopts the odd-tree `A+(C-B)` representation and the flatten/simplify identities wholesale under **ADR-1**; they are correct and cheap. The deviation is the same-change rule, which jj documents as knowingly lossy: "rebasing a commit onto a commit that has the same changes (or a subset thereof) and then rebasing it back will lose changes." The docs cite bug #6369 as the real-life example — and #6369's actual title is "**A crisscross merge leads to losing changes**." Its repro is `E = merge(merge(A,B), merge(A,B))` recovering pre-change content, with no rebase anywhere in it. That matters enormously for Lattice: removing rebase does *not* dodge this bug, because Lattice keeps merges and makes them non-blocking. Lattice still auto-resolves, but writes each auto-resolution as a typed resolution event in the op log so the loss is reconstructible, and ADR-1 must pin the criss-cross case as a named test in the G0.3 merge-replay corpus.

**3.4 Conflict round-trips are byte-exact.** jj #9868 (2026-07-26) shows `materialize_merge_result_to_bytes` → `parse_conflict` dropping a trailing `\r` from a conflict side. For Lattice that is a **G1.2** (HARD, 0) byte-fidelity violation, not a bug report, and the adversarial corpus must carry CRLF-terminated conflict sides explicitly.

**3.5 CDC is built and benchmarked, where jj has one roadmap sentence.** All content goes through FastCDC-family chunking with BLAKE3 addressing; parameters are fixed by **ADR-2** against measurement, not defaults. **G1.8** (SOFT, perf): p95 new bytes persisted for a 1-byte edit in a 50 MB file < 262,144 over 100 trials × 5 file types. **G1.9** (SOFT, perf, dual baseline): store size must come in under restic × 1.25 *and* git-gc × 1.5 simultaneously — the second baseline exists so chunking cannot be declared a win by beating only the weaker comparator.

**3.6 Retention is per-tier and logged, not a blanket clock.** jj's GC is `jj op abandon ..<op>` then `jj util gc`, pruning obsolete objects and operations older than two weeks by default, with `--expire` currently accepting only the literal string `"now"`. Lattice's three tiers make checkpointed objects *structurally* ineligible for collection, and every thinning of an ephemeral autosnapshot is itself an op-log entry. **G2.8** (HARD): 0 checkpointed objects collected and 0 thinnings absent from the op log, over year-long traces. Lattice also owes what jj lacks — collection of unreachable index tables ("There's no garbage collection of unreachable tables yet") — which belongs in the same tier policy, not in a separate never-scheduled task.

**3.7 Lenses are the one capability with no jj analogue.** jj's templates (`-T`) format output; revsets select commits. Neither is a shareable, versioned, structural projection of history. Lenses are gated at **G2.7** (HARD, 0 information-loss or reconstruction failures over ≥10,000 generated cases) and **G3.6** (SOFT, 100% of Git publishes lens-defined, with every rewrite-desire incident logged — a deliberately falsifiable claim; see the risk section).

**3.8 Provenance is attached to objects, shared, signed and indexed.** jj #8166 ("design: Add support for per-revision metadata," open since 2025-11-28) scopes metadata to "live entirely locally, with no prescribed method of pushing it to a remote," and von Zweigbergk named the blocker himself: "attaching notes to change ids may not work using Git notes because I think Git notes can only be attached to existing objects (and we don't model changes as Git objects)." Lattice attaches Ed25519-signed provenance to *checkpoints*, which are addressable objects, sidestepping that blocker structurally. **G5.1** (HARD, 0 incorrect provenance query results on a ≥1000-checkpoint ground-truth suite), **G5.2** (HARD, 0 undetected attestation tampering), **G5.4** (SOFT, `ltx trace --agent --unreviewed --touching <path>` p95 < 200 ms). The demand is documented and unmet: jj #9561 (2026-05-26) asks for native agent-session syncing and was deferred by a maintainer to #8166 with "at the end of the year we will probably have a better idea"; a commenter on #8166 wants prompts attached to changes so a model upgrade can drive a "prompt rebase."

**3.9 Lattice deliberately does less, and fuzzes what jj could not.** jj's roadmap includes forge-submit commands, submodules, a cloud repo server plus caching daemon, a VFS, an RPC API and backend-level copy tracking. Lattice v1 ships none of hosting, VFS, submodules or forge-submit, and treats copy/rename as *derived* from the non-authoritative semantic index (**G4.7**: 0 query divergences after index delete-and-regenerate). It picks one store backend by benchmark under **ADR-3** rather than shipping jj's pluggable-backend abstraction, whose cost is visible in `SimpleBackend` remaining a perpetual proof of concept. And because #2193 shows the change-ID index, not the content store, is the weak link, **G1.4** (HARD, 8 workspaces × 10,000 ops) must fuzz the change-ID and provenance indexes, including under a filesystem that does not honour locks.

### Residual risk for Lattice

- **Continuous snapshotting is jj's unsolved cost, plus chunking, and a watcher may not save it.** **G1.5** (`ltx status` p95 < 100 ms, *watcher resident*) and **G1.6** (`ltx save` p95 < 250 ms) are both SOFT. G1.5's number is exactly the "acceptable ~100ms" jj's own contributors targeted in August 2023 and have not reached on large repos three years later — on a fresh `zed` clone it is 1.2s. Worse, the watcher premise is not safe: on JetBrains/kotlin, Watchman changed nothing because the cost was ref/index import. Lattice's op log and provenance index are a *larger* per-command load than jj's refs. These will be the first gates waived, and waiving them removes the only measured defence of the model's usability.
- **Conflicts crossing the bridge will leak, and agents are the vector.** jj needed a non-standard header *plus* decoy directories, and #9571 shows conflict commits reaching a real public repo anyway once plain `git` was in the loop — with "AI agents" named as the likely cause. Lattice's byte-fidelity promise (G1.2) is stricter than jj's, its agent population is larger by design, and G3.3's target is 0.
- **Criss-cross merges, not rebase, are where "no data loss" gets tested.** Lattice removes rebase and keeps non-blocking merges. #6369's loss arises from merges alone. The auto-resolution log (3.3) makes the loss *reconstructible*, not *absent* — G6.1's data-loss hunter must be pointed at criss-cross topologies specifically or it will not find this class.
- **`ltx undo` "undoes syncs" is bounded by physics.** The remote is not yours. A signed retraction is a better answer than jj's, but it is a *compensating action*, not an undo, and G1.3 must not be allowed to score it as one.
- **The identity sidecar is unbounded in jj and larger in Lattice.** "There's no garbage collection of unreachable tables yet." Lattice's provenance index is strictly bigger; G2.8 covers checkpoint objects, not index tables, so an index-growth gate is currently missing from the registry.

### Where the evidence says a Lattice target is unrealistic

**The seven-noun budget (G2.3, HARD, 0 violations).** jj began with the same minimalism and now ships sixteen-plus user-facing terms, with its own advocates documenting terminology inconsistency and its FAQ's first entry explaining a noun's behaviour. Lattice's seven nouns must absorb changesets, durability tiers, provenance, redaction, attestations, conflicts and the operation log as *non-nouns*. On jj's evidence this is the least likely HARD gate in the registry to survive first contact with real users — and unlike the perf gates, it cannot be waived.

**G3.6's 100% lens-defined publishes.** A lens-generated Git history re-derives commit IDs whenever the lens or the underlying record changes. To the forge, that is a force-push — the exact thing jj's users hit in #4285. Lattice has deleted the *concept* of force-push from its own model while still emitting its effects into someone else's. G3.6 is SOFT, which is the right classification; the spec's prose should match it.

**Resourcing, restated with the fuller fact.** It is not only that the creator of the closest prior art concluded "the storage layer has to change to match the model, and that work can be better supported by a company than an open source project." It is that `docs/paid_contributors.md` now lists ERSC ahead of Google with eight jj contributors, and ERSC's stated mission — "creating the building blocks for human ↔ machine collaboration" — is Lattice's differentiator, not merely its storage layer. Lattice is not racing a roadmap sentence written by volunteers who "cannot attach any target dates." It is racing a funded team that owns the upstream.
