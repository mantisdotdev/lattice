# gitoxide and libgit2

> Two attempts to make Git a library rather than a program. **libgit2** is a C library under GPLv2-with-a-linking-exception, at v1.9.7 (13 August 2026); its own site advertises production use and its README scopes it as "a portable, pure C implementation of the Git core methods provided as a linkable library." **gitoxide** (`gix`) is Sebastian Thiel's pure-Rust reimplementation, dual-licensed MIT/Apache-2.0, ~65 workspace crates, at v0.87.1 (24 August 2026) — the 72nd published version since `git-repository` was renamed to `gix` in February 2023, and still not 1.0. Cargo's `Cargo.toml` consumes it. Both projects are healthy; neither replaced C Git, and neither ever tried to.

## 1. What did it get right?

### A borrowed byte-faithful view alongside an owned typed view

`gix_object::CommitRef` stores `author`/`committer` as `&'a BStr` — documented as "the raw author header value as encountered during parsing" — and `extra_headers: Vec<(&'a BStr, Cow<'a, BStr>)>` "in order of them being encountered." The two `WriteTo` impls diverge exactly where fidelity lives:

```rust
// CommitRef::write_to
encode::trusted_header_field(b"author", self.author.as_ref(), &mut out)?;
// Commit::write_to
let mut buf = gix_date::parse::TimeBuf::default();
encode::trusted_header_signature(b"author", &self.author.to_ref(&mut buf), &mut out)?;
```

The borrowed view passes raw bytes through; the owned view re-serializes a parsed `gix_actor::Signature` through a date formatter. That is the single most transferable idea here — **but the draft claim that a `CommitRef` decode/encode cycle is "a byte copy" is false, and gitoxide's own tracker proves it.** Issue #2177, "The `CommitRef` from `invalid_email_or_committer` test cannot be materialized or round-tripped" (open 19 Sep 2025 – 30 Nov 2025), is precisely a `CommitRef` that fails to round-trip. Independently, `CommitRef::write_to` re-emits `tree` and `parent` via `self.tree()` — parsing the stored hex into an `ObjectId` and re-formatting it — and re-emits `encoding` at a fixed position rather than its encountered one. The correct lesson is narrower and more useful: *byte preservation must be a property of the storage layer, not of a parser's borrowed variant.* Gitoxide converged on this itself — the fix for #1923 changed `SignatureRef`'s time from a structured `gix_date::Time` to a raw string.

### Crate granularity as a dependency-cost mechanism

~65 crates against libgit2's single artifact. `gix-hash`, `gix-object`, `gix-pack`, `gix-odb`, `gix-ref` version and publish independently; `gix` re-exports them behind features. A consumer that only parses objects links nothing that opens a socket. Cargo exploits this precisely: `gix = { version = "0.85.0", default-features = false, features = ["sha1", "progress-tree", "parallel", "dirwalk", "status"] }`.

### A published stability contract, honestly applied

`STABILITY.md` defines tiers and the README assigns crates. As of August 2026 exactly **two** crates are Production Grade — `gix-lock` (tier 1) and `gix-tempfile` (tier 2). `gix-hash`, `gix-actor`, `gix-ref`, `gix-config`, `gix-config-value`, `gix-glob`, `gix-mailmap`, `gix-chunk` are Stabilization Candidates. `gix`, `gix-object`, `gix-pack`, `gix-odb`, `gix-protocol`, `gix-transport`, `gix-index`, `gix-url` and the rest are Initial Development. A maintainer who tells you which parts to distrust is worth more than a version number that lies.

### libgit2: backend abstraction and conformance-as-a-binary

Pluggable ODB and refdb backends let a platform swap storage under an unchanged object API. Two practices are worth copying outright. First, libgit2 defaults `USE_SHA1` to the collision-detecting backend and, in v1.9.0 (28 December 2024), added a **cmake-configure-time warning** if you select a plain SHA-1 backend: "Users are encouraged to use SHA1DC, which is _git's hash_." Second, it grew a git-compatible CLI (`src/cli/README.md`: "A git-compatible command-line interface that uses libgit2") whose v1.9.0 changelog rationale is explicit — `blame` and `init` "have allowed for further benchmarking and several API improvements and git compatibility updates," feeding a public benchmark suite. A conformance harness disguised as a binary. libgit2 also has a working `git_packbuilder` doing threaded delta generation, and a working push.

### Parallel pack indexing — with the caveats attached

gitoxide's `index-pack` splits a single-threaded scan from lock-free multi-threaded delta resolution. The often-cited numbers (discussion #82) are from **May 2021**, on an M1: Linux kernel — gitoxide 43.75 s / 2.42 GB peak RSS vs git 83.92 s / 2.68 GB; Android base — gitoxide 114.23 s / 5.02 GB vs git 130.18 s / 3.56 GB. The maintainer's own annotations matter more than the ratios: "we don't actually write the index, whereas git does," the run used "unoptimized Sha1 computation," and on memory — "it keeps the base objects in memory to be able to process its direct deltas… Maybe there is a bug there?" **Cite these as a five-year-old, non-apples-to-apples illustration of a memory profile, never as a current benchmark.**

## 2. Why didn't it win (or why is it niche)?

Neither is in decline; both won the niche they aimed at. The reasons are stated by the designers themselves.

**They declared the goal out of scope.** libgit2's README: "It does not aim to replace the git tool or its user-facing commands." gitoxide's README lists as an explicit **non-goal** replicating "`git` command functionality perfectly — `git` is `git`," while committing only to on-disk format compatibility: "the on-disk format must remain compatible, and we will never contend with it."

**Conformance has no spec, only a reference implementation.** libgit2's README concedes it must "adjust to changes made upstream," "may lag behind in some areas," and tracks incompatibilities under a `git change` label. The lag is long: per-worktree references and `GIT_CONFIG_LEVEL_WORKTREE` landed in v1.8.0 (20 March 2024), roughly nine years after Git 2.5 shipped worktrees. Partial clone (#5564, open since June 2020) and reftable (#5352, open since January 2020) remain unimplemented. v1.9.0 is "expected to be the final release in the libgit2 v1.x lineage," with SHA-256 moving out of experimental only in an ABI-breaking v2.0. gitoxide's `crate-status.md` shows the same asymptote: `gix-protocol` `[ ] push`, `[ ] send-pack / receive-pack client plumbing`, `[ ] report-status, sideband, delete-refs, push-options and atomic pushes`, `[ ] object-format negotiation`; `gix-pack` `[ ] delta compression`; `gix-reftable` entirely unchecked; `gix-index` `[ ] add and remove entries`; `gix-diff` `[ ] diff-heuristics match Git perfectly`. Issue #306, "client push to remote," is closed **not planned**.

**But that inventory is itself unreliable, and this is the trap for a build-vs-buy decision.** `crate-status.md` lists `gix-filter` as `[ ] clean filter base / [ ] smudge filter base / [ ] filter process base` — yet `gix-filter/src/lib.rs` ships `Pipeline`, `driver` (external filter processes), `eol`, `ident` and `worktree` encoding, and `gix-worktree-state`'s own section marks `[x] filter processes` and `[x] single-invocation clean/smudge filters`. Likewise `[ ] create signed commits and tags`, while the August 2026 report announces "signature verification and signing itself, and OpenPGP, X.509, and SSH are all supported and tested." **Unchecked boxes are evidence of documentation lag as often as of missing features. Any Lattice decision citing a checkbox must be re-verified against the crate source at pin time.**

**Reimplementation re-runs C Git's bug history.** gitoxide absorbed a decade of Git's security lessons in about two years: CVE-2024-35186 (RUSTSEC-2024-0348 `gix-index`, -0349 `gix-worktree`, -0350 `gix-fs`) — "During checkout, gitoxide does not verify that paths point to locations in the working tree," vector `AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:H` = 8.8; CVE-2024-35197 (-0351, -0352, -0353) for Windows device names; RUSTSEC-2024-0355/0367/0371 in `gix-path`; RUSTSEC-2024-0359, an unsoundness in `gix-attributes` creating a `&str` from non-UTF-8 bytes and leaking it to `kstring` and `serde`; CVE-2025-22620 / RUSTSEC-2025-0001, where `gix-worktree-state` checkout left executable files world-writable; and CVE-2025-31130 / RUSTSEC-2025-0021, plain SHA-1 with no collision detection — the mitigation C Git shipped in 2.13.0 in 2017 — patched only in `gix-features` 0.41.0 (3 April 2025).

**Ecosystem gravity and churn.** Cargo, the flagship citation, still gates gitoxide behind nightly `-Zgitoxide`: 3.5 years after tracking issue #11813 opened (9 March 2023) only `fetch` is implemented, `checkout` is still marked *(planned)* in `unstable.md`, and the tracking issue has not been updated since **30 May 2024**. Its open blockers are `file://` without the git binary, `ssh://` without the ssh binary, and authentication parity — *not* rsproxy.cn, which is checked off as resolved. Cargo's manifest carries `gix` 0.85 **and** `git2` 0.21 **and** `git2-curl` 0.22 **and** `libgit2-sys` 0.18.5 simultaneously, pinned two minor versions behind current gix. Meanwhile `gix` shipped 0.74 → 0.87 — thirteen breaking minor bumps — between October 2025 and August 2026. Adoption follows: `git2` has 111.4 M lifetime / 15.5 M recent-90-day downloads against `gix`'s 44.8 M / 9.6 M.

**Attention, not headcount, is the constraint.** The February 2025 report opens "I seem to have nothing to write about," then explains that GitButler consumed two months. The August 2026 report covers Git notes, signing, and merge-ORT conformity under an explicit heading: "**No Git3/Reftable progress.**" That same report merged 48 community PRs, so "bus factor of one" overstates it — but there is one lead maintainer setting direction, his attention is periodically captured by adjacent products (GitButler, now his own `tix` CLI), and push, reftable and SHA-256 are what gets deferred.

## 3. What will Lattice do differently, concretely?

### The licence question, settled

**libgit2's licence is not the blocker; the inability to patch it is.** The `COPYING` exception gives "unlimited permission to link the compiled version of this library into combinations with other programs," and maintainer Vicent Martí closed issue #567 in 2012 with "This should be fully compatible with Apache 2.0," which the reporter accepted. So an Apache-2.0 Lattice *may* statically link libgit2. What it may not do is patch it: the same paragraph states the GPL restrictions "cover modification of the file," so modifications stay GPLv2-only, and the FSF holds Apache-2.0 incompatible with GPLv2 — no Lattice source could ever move into such a patch. For a subsystem under a fidelity HARD gate, "we cannot fix the library we depend on" is disqualifying on its own.

**ADR-BRIDGE-LIC (proposed, blocking).** Lattice does not link libgit2. Recorded rationale: the one-way patch valve — *not* licence incompatibility, which would be factually wrong and would not survive review. **Checkable:** `deny.toml` gains `[bans] deny = [{ name = "libgit2-sys" }, { name = "git2" }]`, plus a CI assertion that both entries are present. A licence allow-list is insufficient, and this is verified rather than asserted: downloading `libgit2-sys-0.18.8+1.9.7.crate` yields a package that declares `MIT OR Apache-2.0` on crates.io, ships `LICENSE-APACHE`/`LICENSE-MIT` at its root, and vendors `libgit2/COPYING` (GPLv2 + linking exception) alongside **202 `.c` files under `libgit2/src/`** that its build script compiles. `cargo deny licenses` passes it silently.

### Build-vs-buy: buy the read path, build the write path

**ADR-BRIDGE-DEPS (proposed).** Depend on, read path only: `gix-hash`, `gix-actor`, `gix-date`, `gix-validate`, `gix-object`, `gix-pack`, `gix-odb`, `gix-ref`, `gix-config`, `gix-config-value`, `gix-url`, `gix-refspec`, `gix-glob`, `gix-ignore`, `gix-pathspec`, `gix-discover`, `gix-index` (read), `gix-packetline`, `gix-transport`, `gix-protocol` (fetch + ls-refs only), `gix-credentials`. `gix-attributes` moves to a **conditional** buy pending review of RUSTSEC-2024-0359 and of `crate-status.md`'s unchecked "attributes stack for matching paths to their attributes."

The honest framing of that list: **none of these crates is Production Grade.** Six (`gix-hash`, `gix-actor`, `gix-ref`, `gix-config`, `gix-config-value`, `gix-glob`) are Stabilization Candidates; the remaining fifteen are Initial Development. The buy decision is therefore a bet on a pre-1.0 dependency, and it must be written up as one. The draft's rationale that these are "exactly the crates whose on-disk-format compatibility gitoxide has promised never to contend with" is also wrong for half the list — `gix-transport`, `gix-protocol`, `gix-credentials` and `gix-url` are wire and configuration crates, covered by no such promise.

**Do not depend on:** `gix-worktree-state` and `gix-status` (Lattice has no staging area and continuously autosnapshots; adopting Git's checkout semantics imports the model *and* two CVE classes), `gix-merge`/`gix-diff` for anything user-visible (`gix-diff` marks `[ ] diff-heuristics match Git perfectly`, and `gix-merge`'s own status says of its tree logic: "rewrite so that the whole logic can be proven to be correct - it's too insane now"), `gix-reftable` (empty). **`gix-filter` is excluded on model grounds — Lattice does not run clean/smudge filters — and explicitly not on the false grounds that it is unimplemented.**

**Lattice must implement itself:**

1. **A send-pack/receive-pack client** — report-status, sideband-64k, delete-refs, push-options, atomic pushes, object-format negotiation. `gix-protocol` leaves every one unchecked and issue #306 is closed not-planned. Largest single item in the bridge; budget it as such (ADR-BRIDGE-XPORT).
2. **Delta search for generated packs** (ADR-BRIDGE-PACK). `gix-pack`'s `Entry::from_pack_entry` preserves an existing `OfsDelta` as `DeltaRef`; `Entry::from_data` unconditionally yields `Kind::Base(obj.kind)`. Lattice stores CDC chunks, not Git packs, so the `from_pack_entry` path is *never* available — **every** object it pushes takes `from_data`. Either implement delta search or record a measured, accepted wire cost with a number in it.
3. **A byte-faithful Git object shadow store** (ADR-BRIDGE-SHADOW): `ltx-gitcompat` stores each *imported* Git object as its exact byte buffer keyed by its SHA-1, chunked into the CDC store. Re-emission of an unmodified imported object is a buffer copy. This makes fidelity structural **for the adopt-and-return path only** — see residual risk.
4. **SHA-1DC** (ADR-BRIDGE-HASH): `sha1-checked` (stable line 0.10.0, March 2024 — 0.11.0-rc.0 is a pre-release; pin the stable and track it as a single-purpose supply-chain dependency), erroring on `CollisionResult::Collision`, matching C Git since 2.13.0. Pin `gix-features >= 0.41.0`.

**ADR-BRIDGE-ISO (proposed).** Exactly one workspace crate, `ltx-gitcompat`, may name a `gix-*` type; every other crate sees Lattice's own types. **Checkable:** CI fails on any `gix` import outside `ltx-gitcompat/`. This bounds thirteen-breaking-minors-per-ten-months to one crate and keeps hand-written parsers as a live option.

### Residual risk for Lattice

- **The byte-cache does not cover the path that matters.** A shadow store keyed by SHA-1 only holds objects Lattice *imported*. Lattice's Git-facing history is lens-generated: those commits and trees never existed in Git, so no stored bytes exist and they **must** be serialized from Lattice's typed model — the exact `Commit::write_to` path that loses `+051800`. Fidelity is structural for adopt-then-push-back-unchanged and merely statistical for every other push. Either the gate is scoped to the round-trip path and says so, or the serializer needs the same adversarial corpus.
- **The shadow store doubles adopt-time storage.** Each imported object is stored twice: as its Git byte buffer and as Lattice content. Deduplication across the two representations is partial at best (zlib-framed Git objects chunk differently from raw content). Adopting a monorepo therefore costs roughly 2× on disk — against the thesis that Lattice fixes storage.
- **The bought fetch path has a documented hang.** `SHORTCOMINGS.md`: "Fetches using protocol V1 and stateful connections, i.e. ssh, git, file, may hang." `ltx sync` over SSH is exactly that shape. It also warns that `gix-pack` mmap "squelch[es] IO errors" and that `gix-url` "might be more restrictive than what Git allows." Every one of those sits inside the buy list.
- **Lattice builds its own checkout, so it re-runs the 2024 CVE class — and a class a path corpus will not catch.** RUSTSEC-2025-0001 was a *permissions* bug: 0777 set through a strategy not subject to umask. The adversarial corpus must assert resulting file modes and symlink targets, not only resolved paths.
- **`gix` has no SHA-256 objects and no reftable**, and the August 2026 report's own heading is "No Git3/Reftable progress." `ltx adopt` has an expiry date it does not control.
- **BLAKE3/FastCDC is a per-push tax.** Every Git-facing blob must be rehydrated from its chunk tree and rehashed with SHA-1DC; that cost scales with pushed content, not with the delta.
- **"Invisible to plain-Git teammates" is bounded to the object graph.** Provenance, op-log and lens data must live somewhere; `refs/lattice/*` or a notes ref appears in `git ls-remote`, and `push --mirror` or server-side GC can drop it silently. Redaction tombstones have no Git representation at all: a redaction cannot propagate through the bridge, only its already-redacted result — which a plain-Git teammate experiences as an unannounced history rewrite.

### Where the prior art says a Lattice target is unrealistic

**The stated gate — 100 % round-trip fidelity across ≥1000 cycles on ≥10 real repos — is too weak, not too strong, and passing it will manufacture false confidence.** Every gitoxide fidelity defect on record was found by one wild input, never by repetition: a tag with no timestamp on the tagger line, from `bridge-utils` (#1542, filed and fixed in two hours); an email whose trailing space was trimmed at parse time, "changing the size of the gix-object and it hash" (PR #1922); a real commit carrying `+051800`, an offset `gix_date::Time` could not represent (#1923); and a `CommitRef` that "cannot be materialized or round-tripped" (#2177). Repeating a cycle 1000 times against a repo that passed once finds none of these — they are input-space bugs, not state-machine bugs.

**Gate G-BRIDGE-FIDELITY (proposed replacement).** (a) Breadth over depth: ≥1000 distinct repositories crawled for object diversity at one cycle each, scored on object-shape coverage, not repo count. (b) A curated pathological corpus seeded from #1542, #1922, #1923 and #2177 — **note that gitoxide #2491 does not belong here; it is an error-message-quality complaint about `\n` in a `.gitconfig` `user.name`, not an object round-trip defect, and citing it as one is a factual error.** (c) The corpus must exercise the *serializer*, not only the shadow store, or it tests the path that cannot fail. Any design in which Lattice parses a Git commit into a typed struct and writes it back is one wild timezone away from failing in production, whatever the cycle count.
