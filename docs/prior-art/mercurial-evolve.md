# Mercurial changeset evolution

> Changeset evolution rewrites history without destroying it. Instead of stripping a rewritten changeset, Mercurial appends an *obsolescence marker* recording that changeset A was superseded by successors A'; the predecessor stays in the changelog, addressable by hash, and is merely filtered out of the default view. The storage and core semantics landed in Mercurial in 2012 — `mercurial/obsolete.py` carries a 2012 copyright naming Pierre-Yves David (email domain `ens-lyon.org`) and Logilab SA; hg-evolve's compatibility shim called the pre-2.3 on-disk layout "prehistoric," and that shim was only removed in hg-evolve 12.0.0. The user-facing commands and the exchange protocol still live in the out-of-tree `hg-evolve` extension, whose CHANGELOG runs from 0.2.0 (2012-06-20) to 12.0.0 (CHANGELOG-dated 2025-11-29, published to PyPI 2026-01-29). In Mercurial 7.2.4 (PyPI 2026-08-11) every `evolution.*` knob is still `section = "experimental"` in `configitems.toml`, `hg help evolution` still says "This feature is still in development," and hg-evolve's README still says, in bold, "The full implementation of the changeset evolution concept is still in progress." Fourteen years. It is the closest direct ancestor of Lattice's lenses and change-ID lineage, and the most instructive failure in this design space.

## 1. What did it get right?

**Rewriting became additive.** Markers append to `.hg/store/obsstore`. Amend, rebase, fold and prune stop being destructive; destruction requires the separate, explicit `hg strip`. This is Lattice's "no data loss" thesis, shipped in 2012, and it works.

**The obsolescence graph as second-order version control.** A marker maps one predecessor to a list of successors. The predecessor/successor relation forms a DAG orthogonal to the changeset DAG — evolve's `concepts.rst`: "the obsolescence graph is second-order version control," with a calculus gloss that makes the changeset DAG the first derivative of the source and the obsolescence DAG the second. That framing is right and Lattice's op log inherits it.

**Phases: a typed mutability boundary, not a convention.** Phases are strictly ordered `secret > draft > public`; only draft and secret are rewritable, enforced in `createmarkers` by `if not prec.mutable(): raise error.Abort("cannot obsolete public changeset")`. Pierre-Yves David on `mercurial_general` (2012-08-02): "The whole point of **public** changeset is to be immutable." Immutability is a property carried by the object and checked by the engine, not force-push etiquette. Lattice's published tier is the same construct and should be enforced at the same depth.

**A real relevance closure for exchange.** `obsstore.relevantmarkers()` defines the subset of the rewrite record a peer needs: "marker that use this changeset as successor; prune marker of direct children on this changeset; recursive application of the two rules on predecessors of these markers." Lattice needs exactly this closure shape the first time it exchanges anything about a superseded or redacted object — and, as §2 shows, needs it index-backed.

**Tombstones that preserve structure.** The v1 binary format stores `P × (20 or 32)` bytes of *parents of the predecessor*, with the parent-count byte using the sentinel `_fm1parentnone = 3` for "no parent data stored." `createmarkers` populates it only on prune (`if not nsucs: npare = ...`). The reason is precise: once a changeset is pruned, its position in the DAG is otherwise unrecoverable. This is exactly what Lattice's redaction tombstones need.

**Naming the failure modes instead of hiding them.** `revset_predicates.unstable()` is literally `orphan ∪ phasedivergent ∪ contentdivergent`, each a cached, queryable predicate (`_computeorphanset` is one ordered sweep: a rev is unstable if any parent is obsolete or unstable). Making trouble first-class and interrogable rather than a wedged repo is right; Lattice's first-class conflict objects are the same instinct, and §3 argues divergence must join them.

## 2. Why didn't it win (or why is it niche)?

**The store never got an index.** `obsstore._data` is `self.svfs.tryread(b'obsstore')` — the whole file, read whole. `_all` parses every marker in it. `successors`, `predecessors` and `children` are each a full linear pass over `_all`, and `relevantmarkers` needs all three. Cost is proportional to every rewrite ever recorded, not to the operation at hand, on an append-only file with no compaction path. The write path has its own quadratic: an inline comment in `createmarkers` notes that creating a marker invalidates the hidden cache, "Resulting in n^2 behavior," worked around by batching. The wiki page `CEDObsstoreFormat` proposed a third on-disk format — a "multi-files (docket, index, data) approche, similar to what we did for Nodemap," radix-tree index, mmap-able "without having to parse the full data for each runs." It was never implemented: `obsolete.py`'s `formats` dict in 7.2.4 registers exactly `_fm0version = 0` and `_fm1version = 1`, and the wiki page has been archived since 2020-09-25. `ChangesetEvolutionDevel` still lists "Better storage//loading//cache for markers" as open — explicitly annotated *"(depends on marker exchange)"*.

**Exchange never converged. This is the real killer.** `CEDObsmarkersExchange` documents the first algorithm, `obshashtree`, failing on two structural grounds: superset detection — if the destination has a superset of the source's markers, it "will be detected as 'different markers on both side' and the source will send everything to the destination again," a case the page notes "will be very common"; and cascade invalidation — because a node's obshash covers pruned children, pruning invalidates "the obshash of an old changeset and all its descendant leading to the resend of all markers applying to 6 months all changesets," and "each new changeset created, adding a new markers to the chain will resend everything in the chain." The replacement, `obshashrange`, does bisection over a stable subdivision of the DAG. It is still not in core. The header of `hgext3rd/evolve/obsdiscovery.py` in hg-evolve 12.0.0 reads: "Status: Experiment in progress // open question. The final discovery algorithm and protocol will go into core when we'll be happy with it." It carries a SQLite-backed range cache and *two* escape hatches: `experimental.obshashrange.max-revs`, documented as "automatically disable obshashrange related computation and capabilities if the repository has more than N revisions… ensuring no large repository will get affected" (`_useobshashrange` returns False, and the wire capability `_evoext_obshashrange_v1` is simply not advertised), and a blunter `evolution.obsdiscovery = no` recommended "For very large repositories." The optimised path is documented as not scaling.

**Partial knowledge silently changes meaning.** `obsutil.successorssets`: "Finally, final successors unknown locally are considered to be pruned." A changeset whose successor you merely have not fetched is reported to you as deleted. In a partially replicated system, the semantics of the record become a function of what you happen to have synced.

**Two authorities can contradict.** Phase-divergence exists only because obsolescence and phases are independent facts that can disagree. The docs leak the resulting ordering constraint into the user's head — `sharing.rst`: "it's important that Bob push to `public` *before* `review`… That could lead to confusion at some point."

**Arity encoding did not hold.** `obsolete.py`'s docstring makes split one marker with N successors, precisely so it is distinguishable from divergence (two independent `(A, (B,))` and `(A, (C,))`). Elegant — and insufficient. Fold could not use it: `createmarkers` rejects multi-predecessor/multi-successor relations ("Fold markers can only have 1 successors") and instead emits N one-to-one markers tagged with out-of-band `fold-id` / `fold-idx` / `fold-size` metadata. Twelve years in, hg-evolve 11.1.6 (2024-11-27) still had to ship "unrelated parts of splits are no longer considered content-divergent," a port of an upstream fix. And the V3 proposal's stated direction is to abandon arity entirely: "Current plan would be to unify on 1-1 markers. It seems simpler, and more extensible."

**Effect flags were designed for an index and then not indexed.** `obsutil.EFFECTFLAGFIELD = b"ef1"` with `DESCCHANGED/METACHANGED/PARENTCHANGED/DIFFCHANGED/USERCHANGED/DATECHANGED/BRANCHCHANGED`. The v1 binary header already contains a `uint16` bit field described as "reserved for flags used in common obsolete marker operations, to avoid repeated decoding of metadata entries" — and the effect flags are not in it. They are written as decimal ASCII into the key/value metadata blob, behind the comment "we plan to extend the existing obsmarkers bit-field when the effect flag design will be stabilized." Nine years later it is still stranded. Answering "which amendments only touched the description?" therefore still costs a full obsstore parse.

**The vocabulary never stabilised.** The CHANGELOG dates the churn: 1.1.0 (2012-10-26) "rename latecomer to bumped" and "renamed conflicting to divergent"; 7.0.0 (2017-11-02) `--contentdivergent`→`--content-divergent`, `--phasedivergent`→`--phase-divergent`; 9.0.0 (2019-06-06) "use 'unstable' instead of 'troubled'"; 10.4.0 (2021-10-12) drop the deprecated `--unstable`, `--divergent`, `--bumped`. One concept, four public names, nine years. The shipped state vocabulary is nine nouns: seven core revset predicates (`obsolete`, `hidden`, `extinct`, `orphan`, `unstable`, `phasedivergent`, `contentdivergent`) plus evolve's `troubled()` (marked "legacy name") and `suspended()`. `concepts.rst` opens with "This document contains math!" and "This document is incomplete!"; `sharing.rst` contains a literal `** STOP HERE: WORK IN PROGRESS **` marker mid-document, routes readers around a live evolve bug (prefer `internal:other` over `internal:local`) via a link annotated "# XXX this link does not work," and concludes that mutable history shared by multiple developers is "a scary place to go… a professional kitchen full of expert chefs tossing their favourite knives back and forth, with the occasional axe or chainsaw thrown in." `CEDUserInterface` records a case where recovery "takes 6 calls to 'hg evolve', the last 4 of which need --any," and a developer asking that the troubled-commits message be actionable: "Currently it just prints the count."

**The biggest users routed around it, then the platform left.** Meta's Sapling *replaced* the obsstore: "Obsstore decides visibility. Mutation does not decide visibility"; Sapling treats commits as invisible by default with shrinkable "visible heads"; and "mutation uses IndexedLog for `O(log N)` lookup. Nothing in Sapling requires `O(N)` loading of the entire mutation data." Mozilla's `moz-phab` treats markers as disposable: when evolve is absent it enables `experimental.evolution.createmarkers` for the run, records `unlink_obsstore = not os.path.exists(self.obsstore)`, warns that running without evolve "usually causes severe performance issues," and on cleanup `os.unlink`s the obsstore it created and runs `hg strip --hidden` because "With the obsstore deleted the amended nodes are no longer hidden." The wiki's `ObsoleteIncompatibleRepository` page — about the forward-compat abort `parsing obsolete marker: unknown version 1` — lists "Periodically delete the obsstore" as a remedy, and calls obsolete markers an experimental feature that "may not be sufficiently forward looking." Then the floor went: Atlassian sunset Mercurial on Bitbucket Cloud (no new hg repos 1 Feb 2020, read-only 1 Jul 2020, disabled by 26 Aug 2020), citing "less than 1%" of new users choosing Mercurial and "about 3% developer adoption" in the Stack Overflow survey; Mozilla moved Firefox's source of truth to Git on 30 April 2025.

**Verdict.** The mechanism is largely correct and worth partially stealing. It lost to (1) an unindexed, uncompactable store whose improvement was explicitly blocked on (2) an exchange protocol that after nine years is still an "open question," (3) a vocabulary that never settled, and (4) the ecosystem evaporating underneath it. Causes 3 and 4 dominate the market outcome — but cause 2 is a real unsolved engineering problem, and it is the one Lattice is walking straight into.

## 3. What will Lattice do differently, concretely?

**Trap 1 — unbounded append-only store with O(N) reads.** A lens is a rule document, not a per-rewrite fact table; its size is O(rules), not O(rewrites). Bind this in **ADR-LENS-001**: *a lens MUST NOT contain per-checkpoint entries; lens rules are predicates over checkpoint attributes*. Gate **G-LENS-SIZE**: generate 100,000 checkpoints under a fixed lens; assert serialized lens bytes are constant and cold-start p99 of `ltx log --lens` is independent of checkpoint count. That gate is necessary but easy — the honest asymmetry is that Lattice *does* have an obsstore-shaped structure: the operation log, plus the change-lineage store of Trap 6. Separate gate **G-OPLOG-INDEX** binds them: for a bounded query (`ltx trace --agent --unreviewed --touching src/auth/`, `ltx undo`, discovery closure) the harness counts records deserialized and asserts that count is bounded by the answer size, not by history length, at 10² / 10⁴ / 10⁶ operations. This is an *admission requirement* on the store benchmark, recorded in **ADR-STORE-001**: a backend that cannot serve indexed prefix and secondary-index lookups over the op log is disqualified before throughput is measured, not traded off against it. Mercurial's ordering — improve storage *after* exchange — is the trap; take it in the reverse order.

**Trap 2 — exchange discovery.** Lattice's native sync is structurally the obshashtree problem: hashes over ranges of a log with a mutable tail, invalidated by late writes to old regions. (a) **ADR-SYNC-001**: negotiation runs over a *stable subdivision* of the checkpoint DAG — obshashrange's actual insight — never per-node hashes an ancestor write can invalidate. (b) Gate **G-SYNC-DISCOVERY** replays the case `CEDObsmarkersExchange` names: append one operation referencing an ancient checkpoint, then sync; assert bytes-on-wire and round trips are O(delta), not O(history). It must also cover the superset case: peer B holds a strict superset of A's operations; assert A→B transfers zero payload bytes. (c) Gate **G-SYNC-LOUD**: no `max-revs`-style silent disable ships. A build in which discovery can fall back without writing a `discovery-degraded` operation into the op log fails the gate, consistent with the rule that autosnapshot thinning is itself logged.

**Trap 3 — partial knowledge silently changing semantics.** The lens evaluator returns a three-valued result per checkpoint — `Present`, `HiddenByRule`, `UnresolvableLocally` — as a Rust enum with no `Default` impl, so a new call site cannot silently collapse the third case. `ltx log` renders `UnresolvableLocally` distinctly and never folds it into hidden. Gate **G-PARTIAL**: clone with a truncated chunk/op set; assert no checkpoint is reported hidden when the cause is missing local data. This is cheap *because lenses are read-path only*: an unresolvable rule is a presentation gap, not a claim about what exists. The same three-valued discipline is mandatory for op-log replay and tombstone application, which are *not* read-path — see Trap 7.

**Trap 4 — two authorities contradicting.** Phase-divergence is the price of obsolescence and phases both having a vote. Lattice's rule: lenses have **no** authority over durability. A lens can never remove a published checkpoint from the record, and tier transitions are never expressible as lens rules. Gate **G-LENS-READONLY**, a property test over generated repositories: for every lens L and repository R, `ltx internals digest R` is byte-identical with L applied, absent, or deleted. That is the mechanical statement of "deleting every lens loses zero information."

**Trap 5 — vocabulary churn.** hg renamed one concept four times over nine years and shipped nine state nouns. Gate **G-NOUNS**: lint every user-facing help string and error message in `ltx`; fail the build on any noun outside the seven plus an explicit, reviewed allowlist, with the allowlist diff requiring the same review as an ADR. Note the gate will immediately fail: divergence (Trap 6) and lineage (Trap 7) need nouns. That is the gate working — the cap is a budget to be spent deliberately, not a claim that no eighth noun exists.

**Trap 6 — divergence.** Orphaning is intrinsic to *destination-changing* rewrites: a lens that squashes A..C does not orphan D, because D still points at the real C. Orphans cannot exist in Lattice. Phase-divergence cannot exist, because no read-path rule can claim a published checkpoint is superseded. **Content-divergence survives**, because Lattice adopts jj-style stable change IDs — and jj independently rediscovered it, ships a "Divergent changes" guide, and has a `jj converge` design document that is still an unimplemented strawman proposal. Gate **G-DIVERGE**: two checkpoints carrying one change ID construct a divergence object, surfaced by `ltx trace` and `ltx log`, resolvable only by a later checkpoint; a build that can produce two visible checkpoints with one change ID and no divergence object fails. Ship it in v1 alongside conflicts. Deferring the resolution story is exactly hg's mistake.

**Trap 7 — the write-path record Lattice has not named.** Lenses are read-path and lose nothing. But "changes carry stable IDs surviving amendment" means an amendment produces a *new* checkpoint bearing an *existing* change ID, and the predecessor→successor relation between them is a write-path fact that must be exchanged for peers to agree on what supersedes what. That is an obsolescence store. Lattice's seven nouns contain no word for it and the spec does not specify it. **ADR-LINEAGE-001** must create it explicitly: a `lineage` store of uniform **1-to-1 typed edges** `(predecessor, successor, kind, group_id)` where `kind ∈ {amend, split, fold, prune, converge}` — following Mercurial's own V3 conclusion that arity encoding should be replaced by 1-1 markers, *not* the 2012 docstring. Multi-part relations are expressed by `group_id` + index, which is what hg was forced into for fold anyway. Arity carries no meaning. Gate **G-LINEAGE-ARITY**: a split of A into B and C and two independent amendments of A into B and C must produce structurally distinct, non-inferable lineage records under every interleaving and partial-replication order.

**Trap 8 — the op log must be a DAG, not a chain.** The spec says "append-only Merkle-linked operation log," which reads as a linear chain. Obsmarkers are a *set*: union merges cleanly, which is why hg could defer discovery for a decade without a correctness bug. A Merkle-linked chain has no union. Two workspaces, or a peer sync, produce two heads that cannot both extend one chain. jj — whose change IDs Lattice borrows — solved this by making the operation log a commit-DAG analogue ("each commit object is instead an 'operation' and each tree object is instead a 'view'"; "normally linear… non-linear if there are divergent operations") and 3-way-merging divergent view objects. **ADR-OPLOG-001**: Lattice's op log is a DAG of operations over repo-state views; concurrent heads are reconciled by a defined 3-way view merge that is itself a logged operation; "append-only" means no operation is ever removed, not that the log is totally ordered. Gate **G-OPLOG-MERGE**: run N concurrent operations across two workspaces and one remote; assert the merged view is order-independent and `ltx undo` from the merged head is well-defined.

**Steal / don't steal.**
- *Steal:* the relevance closure shape (`relevantmarkers`) — but index-backed, per G-OPLOG-INDEX, because hg's closure requires a full parse of everything to compute what to send.
- *Steal:* the v1 parent field. Redaction tombstones record the pre-image's parent links so Merkle structure survives content removal. **ADR-REDACT-001**.
- *Steal, corrected:* effect flags. Every provenance record carries a bitfield of what an amendment changed (description / content / parent / actor / task-link). **ADR-PROV-001** puts it in the record's fixed, indexed header and forbids storing it in a key/value metadata blob — hg put its flags in metadata "while we iterate on the information design," left the purpose-built header bit field empty, and thereby kept the full-parse cost it was meant to remove.
- *Do not steal:* marker-arity discrimination. It failed for fold, needed a 2024 correctness fix for split, and hg's own successor format abandons it. Use ADR-LINEAGE-001's typed 1-1 edges.

### Residual risk for Lattice

1. **Op-log sync is obsmarker exchange with a bigger payload and a harder shape.** hg exchanged an unordered, union-mergeable *set* of rewrite facts and still could not get discovery into core in fourteen years. Lattice proposes to exchange every repo-level operation — including undo-of-undo — over a structure that must also converge. This is the single highest-risk item in the spec, and Trap 8 raises rather than lowers its cost.
2. **Lattice needs an obsolescence store and does not have one.** Trap 7. "Lenses replace rebase" is true and is not the same claim as "lenses remove the need to exchange supersession facts." Until ADR-LINEAGE-001 exists, the spec's cleanest differentiator — read-path-only history shaping — is resting on an unspecified write-path store with hg's exact exchange problem.
3. **Shared lenses re-import marker semantics through the Git bridge.** Lattice→Git published history is lens-defined. Once lenses are shareable and versioned, two teammates holding different versions of one lens produce *different Git history from identical Lattice history* — and because lenses lose nothing, nothing in the record flags the divergence. It is content-divergence relocated into the projection layer and made invisible rather than reported. Mitigation must be mechanical (**ADR-BRIDGE-001**): every Git-bridge export embeds the lens ID and lens content hash in a commit trailer; `ltx sync` refuses to extend a Git branch whose last export names a different lens hash without an explicit, logged operation. Gate **G-BRIDGE-LENS** asserts the refusal.
4. **Undo of a sync is not symmetric.** The Mercurial 2026 London sprint recap notes "some rebases are not properly reversible, 'silently' dropping some potentially crucial changes." Lattice's op log can move a local pointer; it cannot retract a peer's fetch or a Git remote's ref update. Gate **G-UNDO-LOCAL** measures *local* invertibility only, and every operation type carries a `locally-undoable | externally-visible` classification rendered by the CLI.
5. **The redaction protocol is a marker system with a stricter contract than hg ever had.** Signed tombstones that preserve Merkle structure are obsolescence markers whose exchange is a *correctness and safety* requirement: a tombstone that fails to propagate leaves the secret live on a peer. Every pathology in `CEDObsmarkersExchange` — relevance closure cost, cascade invalidation, partial-knowledge semantics — therefore applies with safety consequences. Discovery-negotiated propagation is insufficient. **ADR-REDACT-001** specifies a push-based, acknowledged protocol with per-peer confirmation; gate **G-REDACT-ACK** asserts `ltx internals redaction-status` reports unconfirmed peers indefinitely and never reports a redaction complete on quorum or timeout.
6. **Thinning is the compaction hg never shipped**, and therefore the place where "no checkpointed data is ever lost" can quietly become false. Gate **G-THIN**: property test asserting the set of checkpoint-tier and published-tier objects is byte-identical before and after every generated thinning run.
7. **Ecosystems treat rewrite-record stores as disposable liabilities.** moz-phab deletes the obsstore it created and strips; the wiki lists deletion as a remedy. If Lattice's op log or tombstone store becomes a performance or compatibility liability, users and tools will delete it, and "no data loss" becomes false in practice regardless of the design. G-OPLOG-INDEX is the only real defence: the store must never be the reason something is slow.

### Where the spec looks unrealistic

- **"`ltx undo` undoes everything, including merges, syncs and undo itself"** is over-claimed for anything that left the machine. Restate: undo is total over local repository state; operations with external effects record a compensating operation and are labelled externally-visible.
- **Shipping the Git bridge before the semantic and agent layers, with lens-defined export,** puts the hardest interop surface first while the lens engine is youngest. hg's evidence is unambiguous that the *exchange* half of a rewrite/projection system is what takes a decade, not the local half.
- **"Seven user-facing nouns, total"** — hg intended a small vocabulary and shipped nine state nouns for troubled changesets alone. Divergence and lineage are already required additions. G-NOUNS should be adopted as the mechanism for spending the budget, not as evidence the budget holds.
- **"Bytes are the source of truth; the semantic layer is a derived index"** is the right call and is the one place Lattice is structurally safer than hg — a derived index can be discarded and rebuilt. The op log, lineage store and tombstone store are *not* derived, and the spec should say so explicitly so nobody applies the "regenerable index" intuition to them.
