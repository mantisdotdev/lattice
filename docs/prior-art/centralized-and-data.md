# Dolt, Perforce and Subversion

> Three ancestors, each attacking a different one of Lattice's four theses. **Dolt** (DoltHub, formerly Liquidata; Go; Apache-2.0): a version-controlled SQL database built on the *prolly tree* — "short for 'Probabilistic B-tree'" in DoltHub's own words — which Lattice's chunk/Merkle design is a cousin of whether or not it knows it. **Perforce** (Helix Core / P4 Server, proprietary): the centralized system film, VFX and AAA game studios still choose over Git, because it solves terabyte binary depots and exclusive locking, which Git structurally cannot. **Subversion** (Apache, 1.14 LTS, still shipping security fixes): the cautionary tale — a genuinely simpler model than Git's, with real sparse checkout and real path ACLs, that lost anyway.

## 1. What did it get right?

### Dolt: the prolly tree, and why it is not merely a Merkle tree

A **plain Merkle tree over content-defined chunks** — bup, and roughly what Lattice's "large files become chunk trees" describes — gives content addressing, dedup and O(1) subtree equality, but no ordered index: boundaries are a function of the byte stream, so the structure is a *sequence*, not a *map*.

A **prolly tree** makes the tree content-defined *at every level*. Level 0: sort the key-value pairs, run a chunker across the key stream, each boundary closes a leaf. Then build "a new map of highest keys and content addresses" and run the same chunker over *that*, recursing to a root. The result is a search tree that is also **history-independent** — "No matter which order you insert, update, or delete values, the Prolly tree is the same" — because, "[u]nlike B-trees, Prolly Trees don't require rebalancing operations". The docs demonstrate with keys `(1,2,3,4)`: forwards or backwards insertion yields the same leaves `(1,2)` and `(3,4)`.

History independence is what makes hash-pruned diff *sound*, and that is the sentence Lattice needs. Attach hashes to an ordinary B-tree and diff is still O(n): two trees holding identical rows can have different node boundaries, so hash comparison fails at every level and you fall back to a scan. DoltHub's published table, where *n* is leaf data, *k* average block size, *w* window width: read `logk(n)` for both; write `logk(n)` for a B-tree versus `(1+k/w)*logk(n)` for a prolly tree; **diff `d` versus `n`**; structural sharing ✅ versus ❌.

Two refinements Dolt made over the Noms original, both stealable:

- **Chunk on keys only, not keys and values.** Dolt's stated reasons are two: "If we compute the hash of contents using only keys, any fixed size update to values is guaranteed not to shift the chunk boundary," and "Noms rolling hash function, buzhash, performed poorly for byte streams with low entropy" — time series being the named pathology.
- **CDF-weighted splitting.** Dolt uses a target distribution's cumulative function to set split probability: `(CDF(end) - CDF(start)) / (1 - CDF(start))`, so appending a 64-byte pair to a 2000-byte chunk splits with probability `(CDF(2064) − CDF(2000)) / (1 − CDF(2000))`. The goal: "chunk size normally distributed around 4 kilobytes". *(That a bare hash-threshold test instead yields a geometric length distribution is arithmetic, not a cited claim: a memoryless per-byte Bernoulli boundary test has geometric run lengths.)*

Noms' calibration, still the reference numbers: "the pattern we look for is the 12 high bits being 1. Since this has a probability of 1/2^12, the average chunk size in Noms is 4kb"; "a window size of 64 bytes, so the probability of any 1 bit change moving a boundary is about 64/4kb ~= 0.016"; and "in Noms we use truncated SHA-512". Dolt's storage review pins the truncation: "Their address is the SHA512 checksum of the byte buffer truncated to 20 bytes." *(No public defense of the 160-bit width was found — DoltHub states the choice, it does not argue it. §3.3 argues Lattice must not copy it.)*

### Dolt: conflicts as first-class stored objects

Dolt merges cell-wise. A conflict is a per-column collision: "If, for any column α in the table, into changes the value of column α to be χ, and from changes the value of column α to be γ, where χ is not equal to γ, then there is a conflict. Otherwise, the value of the row in the merged output is equal to the value of the row as it appears in ancestor, with all of the column mutations in into applied to it and all of the column mutations in from applied to it." Storage is the interesting part: "Conflicts in Dolt are stored by primary key along-side the table data for the table, in a separate Prolly-tree from the table data itself," each row holding the value "as it appeared in all three commits involved in the merge: into, from and ancestor." Exposed as `dolt_conflicts_<table>` with `base_`/`our_`/`their_` column prefixes. That is Lattice's "conflicts are first-class objects carrying both sides + base", already shipped, indexed and queryable — with a sting in §2. *(The storage sentence is from DoltHub's 2020 cell-level-merge post and predates Dolt's current storage format; the user-facing behaviour is confirmed in current docs.)*

### Perforce: the client is a cache, the server is the index

Terabyte depots work because of `db.have`, a **server-side** table holding "the list of file revisions most recently synced from the depot into the workspace." `p4 sync` is therefore a server-computed delta needing zero client history; the client stores one revision per mapped file and no DAG. Perforce sizes this honestly — "Allocate 1.5 kilobytes of RAM per file in the depot" — and, crucially, admits the design's own scaling limit: with "many clients syncing a large number of files at the same time, the central table is subject to contention," which is why Perforce ships partitioned workspace types backed by "client-specific `db.have.pt` tables that are independent of the central `db.have` table." Scale-out is topology, not rewrite: a commit server is "the single source of truth for versioned files and metadata," edge servers give "best performance overall because most commands are local," P4P "improves performance by caching frequently transmitted file revisions," and the broker filters or redirects commands.

### Perforce: storage policy as a per-file type; branching that copies nothing

Filetype modifiers encode two decisions Lattice has not made explicitly. On *storage*: `+D` "[s]tores deltas in RCS format"; `+C` "[s]tores the full compressed version of each file revision," the default for binary and for text/unicode/utf16 files over 10 MB; `+F` "[s]tores full file per revision, uncompressed," for large binaries. Note the direction of travel: `+D` was the default for text before 2022.1 and is not any more. Perforce concluded that delta-and-compress is not the universal answer and shipped both escape hatches. On *retention*: `+S` keeps only head; `+Sn` keeps "the most recent *n* revisions ... where *n* is a number from 1 to 10, or 16, 32, 64, 128, 256, or 512," purging older ones on submit. That is a per-path declarative durability tier — policy attached to the path, not the operation.

Branching is a **lazy copy**: "In most cases, `p4 integrate` performs a lazy copy. The contents of the file are not duplicated to multiple locations on the server because the integration record contains sufficient information to reproduce the file." Streams then generate the workspace view declaratively from path rules — `share` (sync, submit, integrate), `isolate` (sync and submit, no integrate), `import` (sync only), `import+` (submittable import), `import&` (one depot path to many view paths, read-only), `exclude` ("cannot be synced, submitted or integrated") — with stream types including `virtual`, "[n]ot a stream but an alternate view of its parent stream," and `task`, which "only promotes edited files to the repository." A virtual stream is structurally a lens: a named declarative projection over a record it does not alter.

### Perforce: exclusive locking that actually holds

"p4 lock allows anyone to open a file for edit, but only the person who locked the file can submit it." The stronger `+l` "prevents more than one user from opening the file," assigned in bulk by server-side `typemap` on path and extension patterns. Epic's Unreal documentation gives the rationale: `.uasset`/`.umap` "are binary, so cannot be opened as text or merged in a text-based merge tool," and so "when working on a file the Editor will lock that file." Perforce markets "Trusted by 19/20 of the top AAA game development studios" (vendor claim, unverified); the real lock-in is that UnrealGameSync and Robomerge are Perforce-shaped.

### Subversion: the parts genuinely better than Git

**Cheap copies** — "you don't need to worry about the repository growing huge—Subversion doesn't actually duplicate any data. Instead, it creates a new directory entry that points to an *existing* tree," and "[i]t doesn't matter how large the directory is—it takes a very tiny, constant amount of time and space." **Sticky sparse checkout** — `--depth empty|files|immediates|infinity`, where *ambient depth* is "the depth persistently recorded by the working copy for that item" and "[t]he working copy remembers the depth you've selected for each item in it until you later change that depth selection," plus `--set-depth exclude` since 1.6, which removes a target "from the working copy entirely," making subtraction from a huge repo possible. **Path-based authorization** — per-path `r`/`rw` rules where "the most specific path always matches first" and "[i]f the user is not mentioned at all, no access is allowed" — structurally impossible under content-addressed whole-history distribution. **Locking** — "A lock token isn't an authentication token, so much as an authorization token," and `svn:needs-lock` makes Subversion "use filesystem-level permissions to make the file read-only—unless, of course, the user has explicitly locked the file," with `--force` to break or steal. And one global monotonic revision integer names a whole-repo state — a real usability win Git gave up.

## 2. Why didn't it win (or why is it niche)?

**Perforce won its market and is still winning.** No decline narrative applies. Its bound is cost, plus the fact that everything outside binary-heavy pipelines went to GitHub — a social outcome, not a technical one. Its one published scaling admission is the `db.have` contention above, and the fix was more topology, not a different model.

**Dolt is niche by construction, and its engineers say why.** The trade is stated flatly: "It's fair to say that Dolt is trading off write efficiency to get its version control capabilities." The mechanism is named: Dolt "misses out on taking as much advantage of write buffering and write optimized data structures like LSMTs as a traditional SQL engine would, partly because of its requirement to materialize the full tree and realize a content address for it so often." The same post rules out columnar storage because inserting one row into a 256-column table means "you need to update at least 256 independent places on disk."

The cost curve is the lesson for Lattice's schedule. DoltHub's own retrospective: "Four years ago DoltDB was about 15x slower than MySQL" (written December 2024). Parity arrived in December 2025 at an overall mean multiple of **0.99** — and immediately before the final optimization round the figure was still 1.16, "meaning we were on average 16% slower." The per-test spread at parity is real: point-select 1.35×, select-random-points 1.66×, read-only 1.38×, read-write 1.26×, against wins elsewhere (covering index scan 0.30×, table scan 0.81×). That is roughly five years of full-time work to close a constant factor on a *narrower* problem than Lattice's — rows have primary keys and bytes do not — and MySQL-wire compatibility gave Dolt every driver for free, yet it displaced nothing.

**Subversion lost on capability, and the evidence is from its own committers.** Stefan Sperling's SVN Day 2012 talk enumerates exactly six tree-conflict cases arising from moves (incoming move vs. local move / delete / edit, and the three mirrors) and concludes: "Modelling a move as copy+delete is insufficient." Worse is what 1.8 scoped — "Non-Goals for 1.8.0: Improve behaviour for incoming (i.e. committed) moves; Store renames in repository filesystem." The fix landed in the *client's* `wc.db` NODES table as `moved_to`/`moved_here` annotations, columns that "are unused in Subversion 1.7" and that 1.8 merely "starts using." Twelve years after 1.0 the repository still could not represent a rename, so a two-way move surfaced as the false conflict "local delete, incoming delete upon update." Merge tracking is the same story: 1.5 shipped `svn:mergeinfo` with ten enumerated known issues — renames (#3128), reflective merges (#2897), cyclic merging (#2837), subtree ranges (#3067), repeat merges (#3056), renamed subtrees (#3174) — including #3157, where merging a branch back without `--reintegrate` leaves trunk's "merge tracking information ... list[ing] revisions before X."

The mental model *was* simpler and it did not save SVN. Stack Overflow's 2022 survey put Git at **93.87%** and Subversion at **5.18%** (n=71,379); among professional developers, 96.65% and 5.96% (n=53,374). *(Multi-select question, so these are usage not exclusivity; Stack Overflow asked it in 2022 and dropped it after, so this is the last clean reading.)* The killers were capability — no offline commit, no cheap local branching, no representable rename — compounded by the cause that dominates all of them: GitHub. SVN is not dead (CVE-2024-46901 affected releases through 1.14.4 and was fixed in the 1.14 LTS line); it is simply no longer chosen.

## 3. What will Lattice do differently, concretely?

### 3.1 Directory nodes become prolly trees — as a new ADR, with a gate

The spec says "Merkle directory trees" without saying how a directory node is shaped, and **ADR-3 fixes the pack format and the redb split but leaves node shape open.** If a node is one object listing all entries (Git's `tree`), a 100,000-entry directory is fully rewritten when one file is added, and directory diff degrades toward O(n).

**ADR-5 (new): LTX directory nodes are prolly trees over the sorted entry-name space,** chunked on the *name* stream only (Dolt's keys-only refinement), so a same-length content-address update can never move a boundary. Two checks, both frozen before G1 implementation per §0.3:

- Property test `history_independence` in `crates/ltx-core`: over ≥10,000 generated directory sets, the root hash is byte-identical across shuffled insertion orders and across delete-then-reinsert.
- **New gate G1-13, "Directory write amplification"**: p95 nodes rewritten when one entry is added to a 100,000-entry directory. HARD, target ≤32 nodes. Harness `harness/g1/g1_13_dir_amplification.py`, added to `harness/gates.toml` and hash-pinned in `harness/FREEZE.json`.

### 3.2 The chunking escape hatch, redesigned — because G1-8 forbids Perforce's version of it

The draft of this analysis proposed a `whole` mode (single chunk, no rolling hash, no zstd) modelled on Perforce's `+F`. **That proposal is withdrawn: it cannot pass a gate Lattice has already frozen.** G1-8 measures "p95 new bytes persisted for a 1-byte edit in a 50MB file (100 trials × 5 file types)" with a target under 262,144 bytes. A `whole`-mode 50 MB asset persists 50 MB on a one-byte edit — three orders of magnitude over budget. Perforce can ship `+F` because Perforce has no dedup obligation; Lattice has one, written down, with a number.

The salvageable half of Perforce's lesson is that **compression and chunking are separate decisions and Lattice has fused them.** `+F` says *uncompressed*, not *unchunked*. So:

- **Chunking policy becomes two independent path-scoped store attributes, not three modes**: `chunk_target` (bytes) and `compress` (`zstd` | `none`), defaulted by content sniff, overridable per path in the store config. `whole` is rejected and the rejection is recorded in ADR-3 with G1-8 as the reason.
- **Every non-default `chunk_target` must still satisfy G1-8**, which caps a coarse target at ≤128 KiB. G1-8's five file types must include an already-compressed binary drawn from the ≥5 GiB G0-5 corpus, so the constraint is actually exercised.
- **New gate G1-14, "Ingest throughput by content class"** (SOFT), on the G0-5 binary corpus: `compress=none` must beat `compress=zstd` by ≥1.3× on ingest wall-clock with dedup ratio within 2%. If it does not, the `compress` attribute is deleted and the binding decision stands vindicated. Either outcome is a result.

### 3.3 Index residency: reopen ADR-3, and refuse the 160-bit address

Dolt's NBS index "is loaded into memory at server start up," and "[f]or a 500Mb database which contains ~300K chunks, the index ends up being 9Mb" — **~30 bytes resident per chunk** (derived arithmetic). ADR-3 chose custom append-only packs with "an immutable sorted index per pack" on a benchmark of **40,000 chunks × 8 KiB**. At 8 KiB chunks a 1 TiB depot is ~1.3×10^8 chunks; at a 4 KiB CDC target, ~2.7×10^8. A Dolt-shaped resident index is then 4–8 GB (derived). **ADR-3's decisive evidence sits three to four orders of magnitude below the scale at which the chosen option's known failure mode appears, and residency was never measured.**

- **ADR-3 gains an index-residency clause and is re-measured at ≥10^8 chunks**, reporting resident bytes per chunk, not only throughput and disk. Proposed budget: ≤512 MiB resident at 10^8 chunks (≤5.4 B/chunk), which forces a paged or per-pack-lazy index rather than a fully-resident one. Failing that budget reopens redb for chunk content despite its measured 3.3× write amplification.
- **Address width is frozen at 32 bytes (BLAKE3-256) in ADR-3, and the 160-bit truncation is explicitly rejected**, with the rejection and its reason recorded. Dolt's 20 bytes is a database-internal choice about the operator's own rows. Lattice ingests third-party content, syncs peer-to-peer, and signs provenance over hashes; Git left 160-bit hashes because "SHA-1 is still weak" and a broken hash means "we could not trust that a given hash value represented the known good version of content that the speaker intended." Note the arithmetic honestly: 20→32 bytes is +60% on the *address field*, but only ~+40% on a Dolt-shaped ~30-byte index entry — which makes the residency budget above harder, not easier, and the two decisions must land in the same ADR revision.
- **Chunk target size is decided in the same revision**, since resident index bytes scale inversely with it and G1-8 caps it from the other side.

DoltHub also reports that "Chunks in isolation compress poorly" and that "NBS doesn't provide us any mechanism to group them together, which would result in much better compression." That is a stated expectation, not a measured result — so the LTX pack builder should sort by similarity before zstd as a *hypothesis tested by G1-9*, not as an assumed win.

### 3.4 Steal Perforce's view; refuse Perforce's `db.have`

Perforce sync is cheap because the server holds per-workspace state — and Perforce's own docs show that state contending under load and needing per-client partitioning to escape. Lattice is local-first and peer-to-peer, so it cannot have `db.have` at all and must pay in *round-trips* what Perforce pays in server RAM. Two commitments:

- **Materialization scope is a declarative path ruleset on the `workspace` noun**, modelled on stream paths, with subtractive `exclude` as the primary verb and SVN's ambient, sticky, per-directory `--set-depth` semantics — SVN added `exclude` in 1.6 precisely because the additive form did not scale. No new noun; G2-3 (HARD, zero user-facing nouns beyond seven) is the lint that keeps it that way.
- **G5-8 is amended (or G5-9 added) to measure protocol round-trips against depth of divergence**, not only "initial transfer as a fraction of full store size." Merkle delta negotiation converging in O(log n) rounds passes; degenerating to O(n) on a wide chunk tree fails. A bytes-only metric cannot see this.
- **Autosnapshot thinning becomes path-scoped and declarative**, shaped like `+Sn` rather than global — and G2-8, which already requires zero "thinnings absent from op-log," is extended to assert per-path policies are honoured. Perforce's purge is silent and irreversible; Lattice's is logged, which is the whole difference.

### 3.5 Exclusive locking: a real gap, and the shape of its fix

**Lattice has no answer — the string `lock` does not appear in the spec — and "structural merge" is not one**: nothing in tree-sitter merges two `.psd` files. Every serious prior system concluded locking is mandatory for un-mergeable binaries: Perforce `+l` via `typemap`, SVN `svn lock` + `svn:needs-lock`, and Git LFS bolted it on. The Git LFS design's actual words are stronger than the paraphrase this analysis previously carried: its purpose is "to discourage (we can never prevent) parallel editing of binary files," with the server as the component that "must atomically check/set". Even the centralized systems call their locks advisory; SVN's book concedes locks are "first and foremost a communication tool."

**Decision: `ltx lock` is an advisory claim scoped to a named `remote`** — the remote is the serialization point Lattice already has and already one of the seven nouns, so no eighth noun appears; G2-3 is the gate that enforces it, and help and error text may not introduce "lock" or "claim" as a noun. The claim is an Ed25519-signed op-log entry, so `ltx trace` shows who held what and when. `ltx sync` refuses to publish a change touching a path under another actor's live claim and names the holder, with an error satisfying G2-4 (recovery action plus causal category). A `.lattice/lockable` pattern file (Perforce `typemap`, SVN `svn:needs-lock`) sets matching working files read-only on materialization. Breaking a claim is itself a signed, logged op — and because `ltx undo` undoes everything, `lock` and `break-lock` join G1-3's command alphabet, so undoing a lock break is exercised by the universal-undo gate rather than discovered in production. Checkable: with no reachable remote, `ltx lock` must fail loudly ("advisory only, remote unreachable") rather than succeed locally; and G5-6's ≥10,000 randomized topologies gain a claim-collision class where two partitioned peers claim the same path and must converge to exactly one holder plus one logged loser.

### 3.6 Lenses must be provably lossless, or they become `svn:mergeinfo`

`svn:mergeinfo` is the exact failure mode: derived metadata bolted onto a byte-level store to make history *look* better, which then had to be stored, propagated and reconciled, and grew subtree mergeinfo, self-referential mergeinfo and ten open issues at ship. G2-7 already exists ("information-loss or reconstruction failures over ≥10000 generated cases", HARD, target 0) but its metric does not obviously cover the two assertions that matter.

**G2-7's harness gains two named assertions**: (a) deleting every lens definition and re-deriving yields a byte-identical checkpoint-DAG root hash *and* an identical op-log root hash; (b) zero store writes occur during lens evaluation. Assertion (b) is additionally enforced at the type level — the lens engine takes a read-only store handle (`&dyn ReadStore`), so a write from lens evaluation is a compile error rather than a test failure.

### 3.7 The Git bridge must decide how it encodes a committed conflict — in ADR-1, before G3

This is the one item on the critical path. **ADR-1 (merge model) must state the encoding for publishing a checkpoint that contains a live conflict object, before any G3 work.** Two admissible answers, and the choice must be recorded: either no lens may publish such a checkpoint and `ltx sync` refuses with a named recovery action (which means merges block, just later), or the chosen textual encoding is entered in **G3-4's lossy-edge ledger** as a documented lossy edge. Silence is not admissible: G3-1 demands 100% round-trip fidelity and G3-3 demands zero anomalies in the Git-only teammate suite, both HARD.

### Residual risk for Lattice

- **"Merges never block" is undercut by the closest architectural cousin.** Dolt stores conflicts exactly as Lattice proposes and still will not let the write path proceed: "Merges with schema conflicts will prevent the merge from completing"; "Dolt will not allow you to commit transactions that have merge conflicts, and will automatically rollback any transaction with merge conflicts"; "Constraint violations from merge detected, cannot commit transaction." Storing conflicts as objects buys queryability, not an unblocked write path — because downstream consumers need a well-defined state. Lattice's downstream consumers are the compiler, the test suite, and the Git bridge.
- **Git has no representation for a committed conflict**, and the Git bridge ships *before* the semantic and agent layers. §3.7 forces the decision; it does not make it free. Whichever branch ADR-1 takes costs something the thesis promised.
- **ADR-3 is Accepted on evidence that cannot see its own risk.** 40,000 chunks decided a design whose known failure mode (Dolt's fully-resident index) appears at 10^8. This is not a claim that packs are wrong; it is a claim that the ADR's confidence is not yet earned at target scale.
- **The security-motivated 32-byte address makes the residency problem worse.** Copying Dolt's 20 bytes would shrink the index ~40% per entry and is exactly the wrong lesson to take from a system whose threat model is "the operator's own rows." Lattice cannot have both the cheap index and the defensible hash; it must pay for the hash and engineer the index.
- **Lattice cannot offer per-path *read* authorization.** Perforce and SVN both do; full content-addressed history distributed to every peer cannot. Redaction handles secrets *after* they leak; partial materialization (§3.4) is a convenience, not a boundary. "This directory must never reach that contractor's clone" is unserved, and must be written into the spec's non-goals so G6-4 (unacknowledged deviations, HARD) covers the omission rather than a user discovering it.
- **The differentiator is dark where the social gravity is.** SVN's defeat was sealed by GitHub, not by mergeinfo. With hosting, review and CI out of scope and published history a lens-generated Git projection, provenance, conflict objects and the op-log are precisely what a teammate reviewing on GitHub cannot see. The agent-native layer's value must be legible entirely inside `ltx` to a single team, or it never compounds. G3-6 ("Lens sufficiency", 100% of Git publishes lens-defined) measures the mechanism; nothing measures whether anyone outside the repo notices the value.
- **Performance targets should be calibrated against Dolt's climb, not against hope.** ~15× slower in 2020, 1.16× in late 2025, 0.99 mean at parity — five years, on a problem with primary keys to lean on, by a funded team. Lattice's continuous auto-snapshotting hits the write path far more often than Git does, and every snapshot materializes content addresses eagerly: DoltHub names that exact requirement as why Dolt forgoes write buffering and LSM-style structures. G1-6's 250 ms p95 for `ltx save` is the gate most exposed to this, and 2–5× slower than Git on write-heavy workloads is the realistic v1 expectation.
- **Write amplification travels with fan-out.** DoltHub's 256-column example generalizes: any Lattice feature that fans one logical change across many content-addressed structures — checkpoint DAG, op-log, provenance index, semantic index, lens caches — pays Dolt's cost multiple times. Each new derived index is a multiplier on `ltx save`, which is why §3.1's proposal to *replace* a side-car index rather than add one is the shape to prefer, and why adopting a prolly-tree provenance index must be a measured decision against ADR-3's redb choice (bench `prototypes/provindex`, judged on G5-4's 200 ms p95 and on sync-delta size), not an assumption.
- **Seven nouns is not a moat.** Perforce exposes depot, stream, client, changelist, label, branch spec, typemap, protections, shelf and job, and dominates its market; SVN exposed roughly four and lost. Noun count is uncorrelated with adoption in this sample. Simplicity is a retention property, not an acquisition one — and §3.5 has already forced a locking verb into the vocabulary. Treat seven as a discipline on the CLI surface enforced by G2-3, never as grounds to decline a capability.
